## 1. Cartographie du cluster [WIP]

### 1.a Perimetre schema PlanSettings (run.py L15-38, StartPlanRequest L41-59)

Le schema declare seulement 2 champs typed :
- `library_path: str` (obligatoire, min_length=1)
- `options: Optional[Dict[str, Any]]`

`model_config = ConfigDict(extra="allow")` => Pydantic ACCEPTE silencieusement TOUTES les autres cles legacy (~50 cles `tmdb_*`, `omdb_*`, `naming_*`, `perceptual_*`, ...) sans typer ni valider. C'est la facade `run_facade.start_plan` (L130-141) qui re-wrappe `{settings: {...}}` puis appelle `_validate_passive(StartPlanRequest, ...)` (passif, log ERROR + fallback).

Implication centrale : un toggle UI absent du dict d'origine cote caller REST sera reconstitue via `_hydrate_settings_from_store` (run_flow_support L614-647 : MERGE persisted then OVERRIDE par caller). Le drop/no-op se produit AVAL, soit dans `_init_tmdb_client` / OMDb branch / `build_cfg_from_settings` qui ignorent silencieusement les cles non lues.

### 1.c Candidats Design Decision (PAS DES BUGS)

- `naming_preset != "custom"` ECRASE deliberement movie_template + tv_template a chaque save (settings_support L1247-1251). C'est volontaire (UX preset reset les templates) — pas un drop silencieux. STOP-REMONTE confirme.
- `_validate_passive` (run_facade L47-89) en mode flag=0 fallback dict si validation echoue : c'est la BACKWARD COMPAT ABSOLUE memorisee, mais 7df3af3e a deja eleve le log a ERROR pour rendre l'avalage visible. Pas un drop a corriger.
- Tous les `perceptual_*` (hors auto_on_scan) sont CONSOMMES uniquement par les endpoints perceptual on-demand, pas pendant le scan. C'est l'ARCHITECTURE (perceptual != quality, memoire user). Le seul reglage qui PROMET un auto-trigger pendant le scan et le FAIT PAS est `perceptual_auto_on_scan`.

### 1.e Pattern sain de reference (tmdb_enabled, repare par a37852aa)

`_init_tmdb_client(settings, ...)` (run_flow_support L190-223) :
- Lit `to_bool(settings.get("tmdb_enabled"), True)` -> bool
- Lit `(settings.get("tmdb_api_key") or "").strip()` -> str
- BRANCHE 1 : `tmdb_enabled AND api_key` -> instancie TmdbClient + log "INFO TMDb: enabled"
- BRANCHE 2 : `tmdb_enabled AND not api_key` -> log "WARN TMDb active mais cle vide" (BRUYANT, observable)
- BRANCHE 3 : `not tmdb_enabled` -> retourne None silencieusement (acceptable car explicite)

CLE DU PATTERN : la branche d'echec d'approvisionnement est BRUYANTE (log WARN + dlog dedicate). Tout futur fix de reglage casse doit reproduire ce contrat : effet ON observable, effet OFF explicite, etat ambigu (toggle ON + dependance manquante) logue WARN/ERROR.
