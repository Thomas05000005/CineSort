### 1.4 Racine commune #2 (410 au lieu de 429) et #4 (X-Request-Id absent)

**Hypothese initiale** : middleware rate-limit et X-Request-Id "non traverses" sur facade ?

**Verifie par lecture code** : FAUX. Les deux chemins traversent les memes middlewares.

**Vraie racine commune** (rappelee dans `BILAN_ITER5` section 4) : le **BYPASS LOOPBACK** de `_check_auth` (L433-462) retourne `True` SANS lire `Authorization` quand les 3 conditions sont reunies :
- `client_ip in _LOCAL_CLIENT_IPS` (L454)
- `self.bind_host == "127.0.0.1"` (L455)
- `bypass_disabled is False` (L451-453)

Consequences observables pour les tests #2 et #4 (qui frappent `/api/get_settings` LEGACY en loopback) :
- L964 `_is_rate_limited()` : loopback est **exempte** (L554) -> rate-limit jamais incremente -> **jamais de 429**.
- L968 `_check_auth()` : bypass loopback retourne True -> **jamais de 401** -> le compteur de failures n'est jamais incremente non plus (le 401 est la source des incrementations via `_send_unauthorized` L572-578).
- L982 `method = self.api_methods.get("get_settings")` : Pass 1 desactivee -> `method is None`.
- L988-1005 garde legacy : path sans `/`, prefixe pas dans `_FACADE_ATTR_NAMES` -> **410 Gone**.
- Le 410 est emis via `_respond_json` (L994) qui appelle `_send_request_id_header` (L607).

**Pour #2 (410 au lieu de 429)** : ce n'est PAS un probleme de middleware non-traverse. C'est le bypass loopback qui annule le rate-limit AVANT meme que le compteur ne soit teste. Une URL legacy avec bypass actif = 410 (legacy guard) ; sans bypass actif (kill-switch + non-loopback) = 401 puis apres 5 echecs = 429. Le 429 est donc atteignable uniquement quand `_check_auth` retourne False ET que le rate-limiter compte les failures.

**Pour #4 (X-Request-Id absent)** : ce N'EST PAS absent dans la production. `_send_request_id_header` est appele dans `_respond_json` (L607), qui est utilise par TOUTES les reponses (401, 410, 429, 200, 500). Le header est emis sur les 410 du legacy guard, sur les 401 de `_send_unauthorized`, sur les 429 de `_is_rate_limited`. Le test #4 ne voit "X-Request-Id absent" que parce que le bypass loopback fait que le test attend un 401 mais recoit un 410 (donc verifie le header sur une reponse 410 qui le porte bien — le test peut etre OK sur le contenu du header mais KO sur le code attendu). A reverifier ITER14 etape 3.
