### 3.d CACHE_PROBE — Cache disque JSON file-based [OPERATIONNEL]

**Statut** : OPERATIONNEL (smoketest local OK 2026-06-10).
**Branche** : `loop/correction-2026-06`.
**Acquis preserves** : identification DECOUPLEE du probe (iter4 racine C) — aucun
appel TMDb / NFO / naming dans le cache disque, le cache disque ne stocke QUE
les sorties ffprobe / mediainfo + leur version normalisee.

#### Mecanisme

Le cache DB `probe_cache` (table SQLite via `ProbeRepository`) reste autoritatif
mais une COUCHE SECONDAIRE cache disque JSON est ajoutee pour deux raisons :

1. **Resilience NAS / SMB** : si la DB SQLite subit `BrokenPipeError` / lock /
   contention WAL sur un partage reseau lent, le fallback disque permet quand
   meme un cache hit (le probe reste dispo).
2. **Independance multi-instance** : un fichier JSON par probe est lisible
   directement, partageable entre instances ou outils externes.

Le cache disque cohabite : lecture DB d'abord, fallback disque si miss / exception ;
ecriture des deux en best-effort. Backward-compat 100% : si tout marche en DB, le
comportement et la perf sont strictement identiques a avant.

#### Fichiers crees / modifies

| Fichier | Role |
|---|---|
| `cinesort/infra/probe/disk_cache.py` (NEW, +212 lignes) | API cache disque : `get_disk_cache`, `upsert_disk_cache`, `clear_disk_cache`, `prune_disk_cache` |
| `cinesort/infra/probe/service.py` (MOD) | 2 helpers prives `_get_probe_cache_combined` + `_upsert_probe_cache_combined` ; routage `probe_file` et `_try_cache_lookup` |

#### Convention de stockage

- Repertoire : `<state_dir>/cache/probe/<hash16>.json`
  (defaut state_dir = `%LOCALAPPDATA%/CineSort`)
- Override : env `CINESORT_PROBE_CACHE_DIR`
- Hash : SHA-256 tronque a 16 hex sur `(path|size|mtime|tool)`
- Format JSON :
  ```json
  {
    "version": 1,
    "key": {"path": "...", "size": ..., "mtime": ..., "tool": "..."},
    "raw_json": {...},
    "normalized_json": {...},
    "ts": 1717891200.123
  }
  ```
- Cle re-verifiee a la lecture (defense contre collision hash ou rename manuel)

#### Configuration

| Env | Defaut | Effet |
|---|---|---|
| `CINESORT_PROBE_DISK_CACHE` | `1` (active) | `0`/`false`/`no`/`off` -> desactive lecture ET ecriture |
| `CINESORT_PROBE_CACHE_DIR` | `<state_dir>/cache/probe` | Override chemin du cache disque |

#### Garde-fous

- **Cap taille fichier** : `DISK_CACHE_MAX_BYTES = 5 MB` (probes normaux pesent
  quelques KB, > 5MB = pollution -> ignore en lecture)
- **Ecriture atomique** : `.tmp.{pid}.{ns}` + `os.replace` pour eviter fichier
  corrompu en cas d'interruption
- **Best-effort partout** : toute exception OSError / JSON / Type est avalee +
  loggee en `debug` -> le cache ne casse JAMAIS le probe
- **Version schema** : `DISK_CACHE_VERSION = 1` ; bump invalide les anciennes
  entrees sans purge explicite
- **Warm-up DB** : sur hit disque + miss DB, on re-promeut vers la DB pour
  rapides les prochains lookups

### 3.e POLLING_UI_BACKOFF — Backoff exponentiel cote UI [OPERATIONNEL]

**Statut** : OPERATIONNEL (2026-06-10).
**Cible mecanique** : marteler `/api/run/get_status` toutes les 2-5s pendant
qu'un probe backend hang ~35s -> requetes accumulees sans signal user
(cf section 2 "Polling UI sans backoff sur degradation").
**Acquis preserves** : identification decouplee du probe intact (iter4), contrats
domain/infra/ui import-linter VERT, mecanique apply non touchee.

#### Modifications

| Fichier | Role |
|---|---|
| `web/dashboard/views/traitement.js` | Refactor polling: `setInterval` fixe -> `setTimeout` recursif avec backoff exponentiel sur erreur |
| `web/shared/components.css` | Badge `traitement-run-backoff` (warning style) "Reconnexion dans Xs" |

#### Mecanisme implemente

1. **Constantes** (top de `traitement.js`) :
   - `POLL_BACKOFF_SEQUENCE_MS = [1000, 2000, 4000, 8000]` (1s, 2s, 4s, 8s plafond)
   - `POLL_BACKOFF_MAX_ATTEMPTS = 8` (plafond souple sur le compteur)
2. **State module-level** :
   - `_pollErrorStreak` : nb echecs consecutifs (0 = nominal, >=1 = backoff)
   - `_pollNextRetryAt` : timestamp ms du prochain tick (consomme par UI countdown)
   - `_pollLastError` : message court derniere cause (transparence visible)
3. **Fetchers `_loadRunInfo` / `_loadRunStatus`** :
   - Retournent desormais un boolean succes (avant : void)
   - Capture cause d'echec dans `_pollLastError` (skip AbortError en unmount)
4. **Boucle polling** :
   - `_pollTick` : execute les 2 fetchers, augmente streak sur echec, reset sur succes
   - `_scheduleNextPoll` : programme prochain `setTimeout` avec interval effectif
   - `_effectivePollInterval` : sequence backoff si streak>=1, sinon `_computePollInterval` contextuel (2/5/1.5s selon step)
5. **UI** :
   - Badge `traitement-run-backoff` injecte dans le header (sous `run-meta`)
   - Affiche `"Reconnexion dans Xs"` + cause + `role=status` (aria-live=polite)
   - Visible UNIQUEMENT en mode degrade (streak>=1) -> aucun bruit en nominal
6. **Reset au unmount** : `_pollErrorStreak`, `_pollNextRetryAt`, `_pollLastError`
   remis a 0/null pour qu'un remount reparte sain.

#### Console debug

Log `[traitement] polling backoff attempt N/M (cause)` cote console F12 a chaque
echec, sans toast utilisateur (UX non intrusive, debug developpeur visible).
