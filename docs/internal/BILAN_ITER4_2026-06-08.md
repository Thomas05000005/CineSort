### Pattern silencieux : sites concernes

     log ERROR mais `_apply_impl("", ...)` est appele quand meme. L'impl gere
     probablement le cas (lookup DB sur run_id vide -> 404), mais l'ERROR log
     est noye.
   - Pas de pattern "settings absents" identique a start_plan.

3. **check_duplicates.request** (RISQUE THEORIQUE FAIBLE)
   - Champ requis : `run_id: str` (min_length=1)
   - Memes considerations que apply.request.
   - Pas de pattern "settings absents".

### Flags potentiellement ignores en silence

Le pattern "settings required mais absents" est SPECIFIQUE a `start_plan` parce
que `PlanSettings` enrobe un dict d'options legacy avec ~50 cles via
`extra="allow"`. Si la validation echoue (par exemple le caller oublie un wrap
ou envoie autre chose qu'un dict), Pydantic raise ValidationError, le fallback
retourne le payload tel quel et le scan utilise un dict appauvri ou degrade.

Cles silencieusement ignorables dans `PlanSettings` si validation skip :
- `library_path` (REQUIS, min_length=1) : si absent -> bug observe iter3 (poster
  TMDb null car scan force fallback sur dossier vide).
- Toutes les options legacy via `extra="allow"` : `tmdb_api_key`, `tmdb_enabled`,
  `jellyfin_url`, `jellyfin_api_key`, `radarr_url`, `radarr_api_key`,
  `plex_url`, `plex_token`, `quality_profile`, `naming_template`, etc. (memoire
  ~50 cles).
- Le caller `RunFacade.start_plan(settings=dict_plat)` peut potentiellement

ils sont des wrappers REST plats (`run_id` + `decisions`). Pas de risque
equivalent.
