### Classification racine ETAPE 1 [OPERATIONNEL]

**RACINE = C (rupture AMONT)** — Pre-autorise pour fix.

**Justification :**

Le smoking gun (`run_flow_support.py` L222 `dlog("start_plan TMDb enabled but api_key empty")`) est l'effet visible d'une **rupture du contrat de transmission settings entre la couche REST et la couche metier**, en AMONT de `_init_tmdb_client`. Demonstration :

1. **PREUVE A non-applicable** (test trop unitaire) : le guard `test_plan_tmdb_enrichment_guard.py` L51-56 construit un `settings` dict qui contient deja `tmdb_api_key="test_tmdb_api_key_xyz"`. Le test mocke `_start_plan_impl` (cf L72 `fake_plan_row`) et verifie uniquement la validation pydantic. Il NE reproduit PAS le flow REST reel ou le payload arrive avec UNIQUEMENT `library_path`. Le fix 7df3af3e (wrap `{settings: settings}`) reste valide pour la branche pydantic mais ne couvre pas la rupture amont.

2. **PREUVE B non-applicable** (2e branche ii.b) : il n'existe pas un 2e site dans `_init_tmdb_client` qui desactiverait TMDb conditionnellement. `run_flow_support.py` L196-223 contient UNE seule branche (`if tmdb_enabled and api_key` / `elif tmdb_enabled`). Le bug n'est pas dans le branchement, il est dans **l'etat du dict `settings` AU MOMENT du branchement**.

3. **PREUVE C confirmee** (rupture AMONT) :
   - `infra/rest_server.py` L987 : `result = method(**params)` — le dispatcher REST unpack le body JSON tel quel, SANS merge avec settings.json on-disk.
   - `ui/api/facades/run_facade.py` L95-141 : `RunFacade.start_plan(settings)` recoit le dict tel quel et delegue a `self._api._start_plan_impl(settings)` L136 SANS hydratation.
   - `ui/api/run_flow_support.py` L614-687 : `_start_plan_impl(api, settings, ...)` traverse `_validate_and_init_plan_context` (L226) puis `_build_plan_job_fn` (L351) qui passe le meme `settings` a `_init_tmdb_client(settings, ...)` L372.
   - **Aucune occurrence** de `load_settings`, `_load_settings`, `_merge_settings`, `read_settings`, ou `get_settings_path` dans `run_flow_support.py` (grep verifie).
   - `_init_tmdb_client` L198 : `api_key = (settings.get("tmdb_api_key") or "").strip()` -> vide car la cle est absente du dict recu.
   - **Coherent avec l'observation Field required: settings** mentionnee dans la trace : meme pattern de payload appauvri.

4. **PREUVE D non-applicable** (decision design) : si l'enrichissement TMDb etait hors start_plan par conception, `_init_tmdb_client` ne serait pas appele dans `_build_plan_job_fn` (L372). Or il l'est, et la branche `if tmdb_enabled and api_key` (L204) initialise un VRAI `TmdbClient`. Le code en place attend explicitement les credentials dans le settings dict de start_plan. Aucun endpoint enrich_plan separe, aucun decorateur `@enrich_after_plan`, aucun hook post-scan. La conception EST que start_plan enrichit. Donc PAS une decision design — vraie rupture de contrat.

**SMOKING GUN file:line :**
- `cinesort/ui/api/run_flow_support.py` L222 : `dlog("start_plan TMDb enabled but api_key empty")`
- Branche d'origine AMONT : `cinesort/ui/api/run_flow_support.py` L198 (`api_key = (settings.get("tmdb_api_key") or "").strip()`) sur dict appauvri venant de `cinesort/ui/api/facades/run_facade.py` L136 (`self._api._start_plan_impl(settings)` sans merge on-disk).

**Cas C => fix pre-autorise :** hydrater le settings dict au point d'entree de `_start_plan_impl` (ou `RunFacade.start_plan`) en mergeant avec le settings.json on-disk (`read_settings(state_dir)` qui dechiffre tmdb_api_key_secret DPAPI), en respectant la priorite "requete override on-disk" pour preserver l'opt-in caller.
