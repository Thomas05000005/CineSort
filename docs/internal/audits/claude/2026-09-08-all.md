## La methode du jour, et pourquoi elle a change

`main` **n'a pas bouge depuis le 2026-08-31** (hors un bump d'action CI le 07). Les six audits des 02 au 07 septembre ont donc porte sur exactement le meme arbre que celui-ci. Relire les memes modules une septieme fois n'avait aucune chance de rendre quoi que ce soit.

Le rapport d'hier laissait deux pistes chiffrees. J'ai pris la seconde — « la zone jamais auditee n'est pas epuisee » — et je l'ai remesuree :

```
grep -rhoE '"module": "[^"]+"' docs/internal/audits/findings/ | sort -u
```

Une soixantaine de modules du perimetre n'ont **jamais** porte un seul finding. **Les deux findings principaux du jour en viennent tous les deux**, et aucun n'aurait ete trouve en relisant `quality_score` ou `naming`.

Mais la zone vierge ne suffisait pas : la plupart de ces modules sont **sains** (lus integralement, cf. la liste plus bas). Ce qui a fait la difference, c'est un **angle** applique a travers eux : *ce que le code attend de son environnement, et qui n'existe pas en production*. Le produit est distribue en **EXE PyInstaller onefile** ; le depot, lui, est teste depuis les sources. Tout ce qui ne franchit pas cette frontiere est invisible a la CI **et** a l'audit de code ordinaire.

C'est cet angle qui a rendu A1. Et c'est en le poussant vers les **frontieres Win32** — l'autre chose que la CI Linux ne peut pas voir — qu'il a rendu A2.

## Corrige

### PR #1235 — `fix(build)` : l'ecran Aide est integralement vide dans l'EXE distribue

`runtime_support.py:676` :

```python
def _repo_root() -> Path:
    return Path(__file__).resolve().parents[3]
```

En bundle **onefile** (`CineSort.spec:447`), cette valeur est `sys._MEIPASS`. `_resolve_doc_safe` y cherche `<racine>/docs/...` — et le spec **n'embarque pas `docs/`**. Les `datas` (ligne 268) portent `web/`, les migrations, `locales/`, les presets, WebView2, cffi/clr_loader/pythonnet, puis `VERSION`, `fpcalc.exe` et `lpips_alexnet.onnx`. Les seules occurrences de « docs » dans le fichier sont des commentaires.

`web/dashboard/views/aide.js` appelle les deux endpoints (`:598`, `:700`) :

| Endpoint | Reponse dans l'EXE |
|---|---|
| `runtime/get_doc` | `ok=false`, `error="Document inconnu : 'user-guide'."` |
| `runtime/search_docs` | `ok=true`, `results=[]` |

Les deux formulations sont trompeuses, chacune a sa maniere : la premiere accuse **l'identifiant** alors que les sept `doc_id` sont bien whitelistes ; la seconde rend un **succes vide** — `_resolve_doc_safe` renvoie `None`, la boucle fait `continue` sur les sept documents, et la fonction conclut `{"ok": True, "results": []}`. Motif connu de ce depot : *un echec devient un succes silencieux*.

**Ce qui rend le mecanisme certain, c'est un cas symetrique dans le meme fichier.** `runtime_support.py:778` fait `_repo_root() / "VERSION"` — et cela fonctionne en bundle **precisement parce que** le spec ajoute `datas += [("VERSION", ".")]`, ajout lui-meme garde par `test_packaging.py::test_version_in_spec_datas`. Meme racine, meme mecanisme, meme remede. `docs/` est la seule ressource lue au runtime qui manquait aux datas.

Sept entrees embarquees, pas `docs/` en entier : `docs/internal/` porte les rapports d'audit et les notes de conception, sans objet dans un binaire public. Le cliquet releve `_DOC_FILES` **a l'AST** et le compare a `DOCS_WHITELIST` — des donnees, pas une chaine de code source. Sans le correctif, l'ancre n'existe pas et deux des trois tests echouent ; le troisieme serait vert sans lui et je le dis dans la PR plutot que de le compter comme une preuve.

## Finding verifie, SANS PR — et la raison compte autant que le finding

### A2 — Le toast Windows part avec un layout `NOTIFYICONDATAW` d'avant Windows 2000 *(sev. 3, issue #1236)*

`infra/notifications.py:43` reserve `128s` pour `szTip`, sous le commentaire « szTip[64] in WCHAR = 128 bytes ». Or `shellapi.h` ne declare `szTip[64]` que sous `NTDDI_VERSION < NTDDI_WIN2K` ; depuis, le champ vaut `WCHAR szTip[128]`, soit **256 octets**. Le commentaire de tete du module annonce pourtant « We use the **V2 layout** ».

`cbSize` etant calcule depuis ce format, il porte l'erreur. **L'ecart vaut exactement `szTip`, sur les deux architectures :**

| | `_STRUCT_SIZE` | `FIELD_OFFSET(…, guidItem)` = `V2_SIZE` | ecart |
|---|---|---|---|
| x64 | **824** | 952 | **128** |
| x86 | **808** | 936 | **128** |

La valeur transmise ne correspond donc a aucune des trois tailles que le shell reconnait — et `cbSize` est le champ par lequel il choisit la version de la structure. Meme en supposant qu'il l'accepte, tout ce qui suit `szTip` est decale de 128 octets : `szInfo` (le corps), `szInfoTitle` (le titre) et `dwInfoFlags` (le niveau). **Ce second point se lit dans le code seul**, sans hypothese sur le comportement du shell.

Second defaut, qui est ce qui a maintenu le premier hors de vue : `show_balloon` **ne lit jamais** le `BOOL` rendu par `Shell_NotifyIconW`, pose `_icon_added = True` meme si `NIM_ADD` a echoue (donc ne reessaiera plus jamais), et rend `True` inconditionnellement — quand sa docstring promet « False on failure ». `notify_service.py:172` en fait `if shown: logger.debug("Notification shown")`.

**Pourquoi personne ne l'a vu** : les seuls tests qui touchent `show_balloon` la **remplacent par un lambda** (`test_notify_service_drain_lifecycle.py:46,131,156`) ; le seul test reel du module porte sur `_encode_wstr` ; et la CI tourne sous Linux, ou `_IS_WINDOWS` fait sortir a la premiere ligne. Le layout n'est exerce **nulle part**.

**Croisement** : l'audit du 2026-08-23 (`t23not02`, confiance 0,92) avait etabli que les six bascules « Notifications desktop » ne gardent **que** `show_balloon`. Si A2 se confirme, ces six reglages ne gouvernent alors rien du tout.

**Pourquoi pas de PR** : le correctif tient en un caractere (`128s` → `256s`), mais le runner d'audit n'execute rien et tourne sous Linux — l'effet d'un changement de layout Win32 n'y est pas observable, et un `1` en retour ne prouverait pas que le titre est au bon offset. Echanger une hypothese contre une autre sur un binaire n'est pas un correctif. L'issue porte le protocole de mesure a executer sur Windows, dont l'etape 1 (relever le retour aujourd'hui ignore) tranche seule.

### A3 — Un troisieme lecteur du canal mort du jeton, dans `app.js` lui-meme *(sev. 1, commentaire sur PR #1225)*

`web/dashboard/app.js:650` : « Le token est passe via `?ntoken=XXX` au boot (cf `_detectNativeBoot`) ». Or `_detectNativeBoot`, quinze lignes plus haut dans **le meme fichier**, lit le **fragment** depuis #1207 — et `app.js:118-124` le documente correctement. Le commentaire nomme la fonction qui le contredit.

C'est du commentaire, aucun comportement n'en depend. Signale en commentaire de #1225 (qui traite exactement les suites de #1207) plutot qu'en issue : trop mince pour un element de backlog. Les trois autres mentions de `?ntoken=` (`state.js:38`, `api.js:273`, `rest_server.py:945-949`) sont **correctes** — ce sont des causes historiques qui expliquent pourquoi le filtre `_URLSAFE_TOKEN_RE` existe. Les rediger ferait perdre sa raison d'etre.
