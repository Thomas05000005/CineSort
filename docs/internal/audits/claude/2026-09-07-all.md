## Corriges

### PR #1231 — `rel(probe)` : le seul ecrivain atomique sans fsync publie un EXECUTABLE

`auto_install._extract_member` ecrit le binaire dans un fichier de travail puis
le publie par `os.replace`, **sans `flush` ni `fsync`**. Le renommage pouvait
donc devenir visible avant les octets : un crash dans cette fenetre publiait un
`ffprobe.exe` / `ffmpeg.exe` / `MediaInfo.exe` **tronque** au chemin final —
que `tools_manager` voit ensuite comme disponible et **lance**.

Seul des **neuf** sites d'ecriture atomique du depot a ne pas porter cette
moitie de l'invariant, alors qu'il est le seul a publier un executable.

**Ce n'est pas un finding neuf** : c'est `f10b47da`, releve le **2026-08-06**
avec une confiance de 0,85, classe `trivial`, et laisse explicitement
« candidat au prochain run, non corrige faute de budget d'ouverture ». Il part
en PR **parce qu'il a deja ete instruit** — meme raisonnement que #1224 pour
`8dfa8aa5`. Le re-signaler une quatrieme fois en rapport n'aurait rien produit.

**Le test n'asserte pas « `os.fsync` a ete appele ».** Une telle assertion
survivrait a la suppression du `flush`, qui est l'autre moitie du defaut. La
sonde observe, AU MOMENT du fsync, la taille deja presente sur le disque :

```
fsync retire  ->  aucune taille observee (ensemble vide)
flush retire  ->  taille amputee du dernier bloc
```

D'ou la charge utile de `_EXTRACT_CHUNK_BYTES + 100` octets : elle force DEUX
ecritures dont une derniere de 100 octets, assez petite pour rester dans le
tampon Python. Avec un seul bloc, le test serait vert sans `flush` — un `write`
plus grand que le tampon part directement sur le disque. C'est le point ou une
batterie naive se serait auto-satisfaite.

### PR #1232 — `fix(maj)` : le cache de mise a jour servait la release d'un AUTRE depot

`update_cache.json` est un fichier **unique par state_dir** et ne portait
aucune trace de sa provenance, alors que `update_github_repo` est un reglage
**modifiable**. Apres un changement de depot, tout lecteur du cache servait
pendant 1 h la release de l'ancien — `latest_version`, `release_url` **et**
`download_url`.

Deux entrees sur trois etaient touchees, et la troisieme masquait le defaut :

```
check_for_update_async  (boot, app.py:331)          -> lit le cache
get_cached_info         (runtime/get_update_info)   -> lit le cache
force_check             (« Verifier maintenant »)   -> ignore le cache
```

Le bouton manuel repartant du reseau, un utilisateur qui teste juste apres le
changement voit la BONNE valeur ; c'est au boot suivant, et sur l'ecran, que
l'ancienne revient.

`get_cached_info` recoit donc le depot elle aussi : la comparaison posee dans
`check_for_updates` seul aurait ete une garde **correcte mais inatteignable**
depuis la surface qui alimente l'ecran — motif deja paye en #1097 et #1053.

### A2 — `adaptive_timeout` : trois affirmations, trois fois l'inverse du code *(sev. 1, cat. 10)*

| L'affirmation | Ou | Ce que fait le code |
|---|---|---|
| « Configuration 1. **Settings (UI)** : `probe_timeout_base_s`, `probe_timeout_per_gb_s`, `probe_timeout_floor_s`, `probe_timeout_ceiling_s` » | docstring du module | ces **4 cles n'existent nulle part** : ni `settings_support`, ni l'ecran, ni un defaut. Seul l'env les regle |
| « l'adaptatif n'est applique que si les autres champs adaptatifs sont absents (**retro-compat ABSOLUE**) » | docstring du module + `service.py:564` | ils sont TOUJOURS absents, et l'adaptatif s'applique TOUJOURS |
| « on log et **clamp** […] retomber sur les **defauts** » | `AdaptiveTimeoutConfig.__post_init__` | il logge, et ne clamp rien ; le repli (`return ceiling`) vit ailleurs et n'est pas « les defauts » |

Consequence observable : `parametres.js:82` expose `probe_timeout_s` avec
`min: 5`, mais `floor = 10` rend **toute valeur sous 10 inatteignable**, et le
timeout reel monte a `base + 5 s/Go`, jusqu'a 300 s. Un utilisateur qui regle
« 5 » sur un fichier de 20 Go obtient **105 s**.

**Ce n'est PAS un bug de comportement, et la distinction est ce qui empeche
d'ouvrir un mauvais correctif.** Le comportement est **grave par des tests** :
`test_probe_adaptive_timeout.py::test_legacy_probe_timeout_s_used_as_base` et
`::test_petit_fichier_clampe_floor_si_base_basse` l'exigent nommement. Le
defaut est donc dans la documentation et dans le libelle de l'ecran — et
choisir entre « aligner `min` sur 10 », « exposer les 4 champs » ou « renommer
le champ » est un arbitrage produit.

### A3 — Le garde-fou de restauration n'est purge par personne *(sev. 2, CWE-400)*

`backup._create_restore_guard` copie la base AVANT de l'ecraser, sous
`{stem}.{ts}Z.before_restore.bak`, dans `target.parent`. Or :

```
rotate_backups        n'est appele QUE par backup_db_with_rotation
backup_db_with_rotation   n'ecrit QUE dans _backup_dir() = <db_dir>/backups/
_create_restore_guard     ecrit dans <db_dir>            <- jamais balaye
```

Aucune autre purge n'existe : `retention_cleanup.py` et `quarantine_ttl.py`
rendent **0 occurrence** de `.bak`. Chaque garde est une copie **complete** de
la base.

Ce qui rend la quantite non triviale : `_attempt_auto_restore` itere jusqu'a
`DEFAULT_MAX_BACKUPS + 2 = 7` candidats et appelle `restore_backup` pour
**chacun** qui passe le pre-ecran. Un seul boot sur base corrompue peut donc
deposer jusqu'a **7 copies completes**, et l'operation se rejoue a chaque
demarrage tant que la corruption persiste. Le mecanisme concu pour proteger les
donnees peut remplir le disque — sur un produit qui embarque par ailleurs un
`disk_space_check`.

**Pourquoi pas de PR** : le correctif consiste a SUPPRIMER des sauvegardes.
C'est un chemin destructif, et je ne peux rien executer pour le prouver. Le
prompt d'audit est explicite : « si le correctif demande une preuve par test,
n'ouvre PAS de PR ».

### A4 — Une beta ne sera jamais notifiee de sa propre stable *(sev. 2)*

`_parse_version` ecarte les suffixes pre-release (`.split("-", 1)[0]`), donc :

```
_compare_versions("1.5.2-beta", "1.5.2")  ->  (1,5,2) vs (1,5,2)  ->  False
```

Or `VERSION` vaut exactement **`1.5.2-beta`**. Le jour ou la `1.5.2` stable
sort, **aucun** utilisateur de la beta n'est averti. Le comportement est
documente (« les suffixes pre-release sont ignores ») mais sa consequence sur
**ce** projet — dont la version porte un suffixe depuis des mois, les jalons
etant marques par des tags `+build` — ne l'est pas.

Pas de PR : traiter `-beta` comme anterieur a la stable change la semantique de
comparaison de versions pour tout le produit. C'est une decision de release.

### A5 — `ffmpeg.exe` n'est jamais installe si `ffprobe.exe` est deja la *(sev. 2, cat. 18)*

`install_ffprobe` retourne des la premiere ligne quand `ffprobe.exe` existe :

```python
ffprobe_path = tools / "ffprobe.exe"
if ffprobe_path.exists():
    return str(ffprobe_path)
```

L'extraction de `ffmpeg.exe` vit **apres**, dans la meme fonction, et
`install_all()` n'a aucune entree dediee a ffmpeg. Or `ffmpeg` est requis par
**tout** le perceptuel — extraction de frames, SSIM, grain, loudnorm, astats,
detection de scenes, empreinte audio.

Cas atteignable : `ffprobe.exe` present sans son voisin (pose a la main,
installe par une version anterieure du code). L'utilisateur clique
« Installer automatiquement », l'operation reussit, et l'analyse perceptuelle
reste indisponible.

**Ce n'est pas silencieux** — `perceptual_support.py:358-367` dit « ou ajoutez
ffmpeg.exe a cote de ffprobe.exe » — ce qui borne la severite. Pas de PR :
retelecharger 105 Mio parce qu'un fichier voisin manque est un arbitrage.
