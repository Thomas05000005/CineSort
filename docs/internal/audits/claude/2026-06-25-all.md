## Findings par categorie

### Categorie 33 — Confusion sentinelle (0 / None / absent) — A1

**A1 (PR #666)** — `domain/conversions.py:139` `to_optional_bool` faisait
`s = str(value or "").strip().lower()`. Le `value or ""` transforme les sentinelles
natives **`False`**, **`0`**, **`0.0`** en `""` -> retour `None` au lieu de `False`.
Asymetrie vs `to_optional_int`/`to_optional_bitrate` qui ont des fast-paths typees.
Impact : `_bool_from_text` (ffprobe/mediainfo, flag `forced` des pistes sous-titres)
recoit un bool natif `False` du parsing JSON -> traite comme "absent" au lieu de
"explicitement faux". Fix : fast-paths `isinstance(value, bool)` / `(int, float)`
**avant** la coercion str. Test neuf `test_optional_bool_preserves_native_false_and_zero`.
Confidence 0.92.

### Categorie 21 — Atomicite I/O — A2

**A2 (issue #669)** — `infra/db/backup.py` :
- `restore_backup` (L220-248) ecrit directement dans la DB live de maniere
  **non-atomique** : si l'ecriture est interrompue (crash, disque plein), la DB
  active est laissee dans un etat partiel/corrompu, sans rollback.
- `backup_db` (L76-79) peut laisser un `.bak` **corrompu** si interrompu en cours
  d'ecriture, qui sera ensuite considere comme un backup valide.

Fix suggere : ecrire dans un fichier temporaire puis `os.replace()` atomique
(meme pattern que `state.atomic_write_json`). **Issue** plutot que PR car le chemin
de restauration est sensible et merite revue + test sur base pre-existante (memoire
user #10). Confidence 0.85.

### Categorie 17 — Idempotence — A7

**A7 (issue #671)** — `app/runtime_probe_check.py:139,195-196`
`cross_check_rows_with_probe` lit `confidence = int(getattr(row,"confidence",0) or 0)`
puis ecrit `row.confidence = max(0, min(100, confidence + bonus))`. **Non-idempotent** :
un second appel (re-check, retry) re-applique le `bonus` -> la confidence derive a la
hausse a chaque passage. Fix suggere : recalculer depuis une base stable (confidence
sans bonus stockee separement, ou flag "deja croise"). **Issue** car corriger
l'idempotence demande de decider ou stocker l'etat "deja applique" (choix de design,
hors niveau modere). Confidence 0.80.

### Categorie 18 — Error handling (except trop etroit) — A6

**A6 (issue #670)** — `app/move_journal.py:94-95` `delete_pending_move` (appele post-move
par `journaled_move`) ne catche que `(sqlite3.Error, OSError, AttributeError)`. Or le
docstring (L13-15) stipule explicitement qu'un echec du journal **ne doit JAMAIS
bloquer un move reussi**. Si le delete leve un autre type (ex. `TypeError` sur un
journal_id malforme), l'exception remonte et fait apparaitre une **fausse erreur** sur
un move qui a en realite reussi physiquement. Fix suggere : elargir a un `except
Exception` log-and-continue **uniquement** sur ce delete post-move (le move lui-meme
garde son handling strict). **Issue** car l'elargissement d'un except touche la
semantique d'erreur d'un chemin critique. Confidence 0.78.

### Categorie 1 + 21 — Bugs latents I/O non gardes — A3, A4

**A3 (PR #667)** — `KeyError` hors du `try` dans deux endpoints dashboard :
- `library_podiums_support.py:48` : `return str(runs[0]["run_id"]) if runs else None`.
  Le `try/except` au-dessus couvre `get_runs_summary` mais **pas** l'acces
  `runs[0]["run_id"]` -> si une ligne run n'a pas la cle, `KeyError` non catche ->
  HTTP 500. Fix : `if not runs: return None` puis
  `str(runs[0].get("run_id") or "") or None`.
- `library_timeline_support.py:225` : meme pattern, fixe identiquement.

Fix safe et local, comportement inchange sauf le cas degenere. Confidence 0.88.

**A4 (PR #668)** — `ui/api/tmdb_support.py:158` `enrich_tmdb_ids_by_title` ouvrait
`plan.jsonl` en lecture **sans garde** : un fichier illisible (permission, encodage
corrompu) -> `OSError`/`UnicodeDecodeError` non catche -> HTTP 500 brut au lieu d'une
erreur metier propre. Fix : wrap dans `try/except (OSError, UnicodeDecodeError)`
retournant `_err_response(f"Plan illisible: {exc}", category="runtime")`. Confidence 0.86.
