## A1 — `video["hlg"]` est ecrite par le scoring, et personne ne la lit *(sev. 3)*

`_merge_probe_with_name_hints` comble les trous du probe avec les indices du nom
de release. `release_name_parser` sait reconnaitre `\bHLG\b`
(`release_name_parser.py:122`), et le bloc de fusion en tire :

```python
# quality_score.py:2373-2375
elif name_info.hdr_hint == "hlg":
    video["hlg"] = True
    filled_from_name.append("hlg")
```

**Cette cle n'a aucun lecteur.** Mesure — `grep '"hlg"'` sur les quatre modules
qui decident quoi que ce soit du HDR (`quality_score`, `naming`,
`library_support`, `dashboard_support`) ne rend que les lignes 2361, 2373-2375
de `quality_score` elles-memes. Le chemin est pourtant complet et verifie :

```
2513  probe, name_filled = _merge_probe_with_name_hints(probe, name_info)
2515  video = probe.get("video")          <- le dict qui porte "hlg"
2538  vr = _score_video(video, prof, ...)
1242  has_dv     = bool(video.get("hdr_dolby_vision"))
1243  has_hdr10p = bool(video.get("hdr10_plus"))
1244  has_hdr10  = bool(video.get("hdr10"))     <- "hlg" n'est jamais lu
1294  if has_dv: ... elif has_hdr10p: ... elif has_hdr10: ...
                                          -> hdr_bonus = 0
```

**Et la garde qui la precede est morte elle aussi.** Ligne 2361,
`has_any_hdr_probe` teste `video.get("hlg")` — une cle qu'AUCUN normaliseur de
probe ne produit (`_normalize_ffprobe` pose `hdr_type`, pas `hlg`) et que seul
le bloc 2374 ecrit, **apres** ce test. Le terme est donc constamment faux.

**Ce que l'utilisateur voit, et c'est le triangle habituel.** `filled_from_name`
alimente un `factors` affiche dans l'explication du score
(`quality_score.py:2525-2533`) :

```
+0 Specs deduites du nom de release: hlg
```

L'application annonce donc avoir deduit le HLG du nom — pour un effet
strictement nul sur le score, le tier, le label et la facette. C'est
« ce qu'on annonce n'est pas ce qu'on a fait », applique a une deduction.

### Verification adversaire

1. **Deja corrige ?** Non. Lu sur `main` a `3fca5ff` ; #1208 ne touche que
   `composite_score_v2`, #1209 que le codec audio, #1210 que le renommage.
2. **La garde existe ailleurs ?** Non — c'est la mesure ci-dessus, faite sur les
   quatre modules consommateurs, pas sur un souvenir.
3. **Chemin inatteignable ?** Non : `parse_release_name` est appelee des que
   `release_name` est fourni (ligne 2512), et `\bHLG\b` est un tag de release
   courant sur les captures broadcast.

### Ce qui CONTRAINT le correctif — mesure, et ce n'est pas un detail

`hdr_type` n'est **pas** disponible partout. `_normalize_merge.py:175-179` ne
propage les champs structures que depuis `ff_video` :

```python
for k, v in ff_video.items():      # ff_video SEULEMENT
    if k in _already_merged: continue
    video[k] = v
```

`_normalize_mediainfo` ne produit **que** les trois booleens (lignes 85-87), pas
`hdr_type`. Sur un poste ou seul MediaInfo est installe, basculer un
consommateur des booleens vers `hdr_type` **eteindrait toute la detection HDR**.

Le correctif doit donc etre **additif** — consulter `hdr_type` *en plus* des
booleens — et non substitutif. C'est exactement le piege « un correctif peut
ETEINDRE une garde existante en la privant de sa matiere », et c'est la raison
pour laquelle ce finding part en **issue et non en PR** : il touche quatre
sites, demande un barème `hlg_bonus` (arbitrage produit, donc migration de
profil) et sa preuve passe par des tests que ce runner ne peut pas executer.

## A3 — Un support inaccessible au boot devient « FICHIER PERDU » *(sev. 2)*

`move_reconciliation._classify_pending` (lignes 160-181) etablit son verdict sur
deux `exists()` dont l'`OSError` est rabattue sur `False` :

```python
try:    src_exists = src.exists()
except OSError: src_exists = False      # NAS deconnecte == fichier absent
...
return "lost"     # « FICHIER PERDU [...] Verifiez vos backups et l'antivirus. »
```

Un NAS non monte au demarrage, apres un crash d'apply, produit donc l'alerte la
plus grave du module — et **l'entree pending est supprimee dans tous les cas**
(ligne 292-295), donc la trace qui aurait permis de rejuger disparait avec elle.
C'est « confondre INCONNU et PIRE », sur le chemin qui existe precisement pour
dire la verite apres un crash. Le verdict honnete serait un quatrieme etat
`indecidable`, qui **conserve** la ligne.

## A4 — `src_size` absent : le trou que #1192 vient de fermer a cote *(sev. 1)*

#1192 (avant-hier) a impose « taille **ET** hash » aux deux verdicts destructifs
de `apply_rollback`, et **refuse** d'ecraser quand `src_size` manque. Le chemin
UNDO garde la forme d'avant (`apply_support.py:200`) :

```python
if expected_size is not None and int(actual_size) != int(expected_size):
```

`expected_size is None` fait **sauter** la comparaison de taille ; seul
`sha1_quick` decide alors — or il ne hache que 8 Mo de tete et 8 Mo de queue.

Le cas n'est pas theorique : la migration 013 ajoute les deux colonnes ensemble
(donc pas de ligne « sha1 sans taille » d'origine), mais
`_journaliser_quarantaine_undo` les calcule **en sequence**
(`apply_support.py:537-541`) — `sha1_quick_cached` d'abord, `dst.stat()`
ensuite, dans le meme `try`. Un `stat()` en echec apres un hash reussi ecrit
exactement la ligne « sha1 present, taille NULL ». Fenetre etroite, sens
permissif sur un chemin destructif.

## A5 — `windows_safe` peut rendre la chaine vide *(sev. 1)*

`path_utils.py:114-118` : le garde `if not name: name = "_untitled"` s'execute
**avant** `return name[:180].rstrip(". ").strip()`. Si les 180 premiers
caracteres sont tous des points ou des espaces, la valeur de retour est `""`.
Le commentaire juste au-dessus montre que la troncature-puis-strip a bien ete
pensee — mais pas qu'elle peut vider ce que le garde venait de remplir.
Population reelle quasi nulle (il faut un titre de 180 caracteres de
ponctuation) : **defense en profondeur**, pas un defaut vecu.
