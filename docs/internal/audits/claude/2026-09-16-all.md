## A1 — Le reglage « Niveau de verbosite » n'atteint pas le fichier de log *(sev. 3)*

**Persona** : RELIABILITY · **Categorie** 19 (coherence backend ↔ UI) · **Confiance** 0,95

Les deux chemins de boot d'`app.py` font, dans cet ordre :

```python
boot_level = resolve_log_level(None)         # settings.json PAS encore lu -> INFO
install_rotating_log(..., level=boot_level)  # handler.setLevel(INFO)
...
effective_level = resolve_log_level(settings.get("log_level"))
logging.getLogger().setLevel(effective_level)    # le ROOT seul bouge
```

Un handler filtre **pour son propre compte** (`record.levelno >= handler.level`). Le handler de fichier reste donc a INFO pendant que le root passe a DEBUG : les records DEBUG sont bien emis, puis **rejetes a l'entree du fichier**.

**Ce que l'utilisateur voit** : Parametres > Logs > « Niveau de verbosite » = DEBUG, sans mention de redemarrage, et rien ne change — pas meme apres redemarrage, puisque le defaut est dans l'ordre du boot, pas dans un hot-reload manquant.

**Pourquoi ca compte ici precisement** : le bundle est construit **sans console** (`/CLAUDE.md`, piege du smoke test PyInstaller), donc `cinesort.log` est le seul canal, et c'est celui que la visionneuse de l'ecran Diagnostics lit — `runtime_support._logs_dir`, dont le commentaire dit « lecteur et ECRIVAIN partagent donc une seule source ». Le seul reglage dont l'objet est de produire un diagnostic n'en produisait aucun.

**Ce qui a masque le defaut** : `CINESORT_DEBUG=1` fonctionne, lui, parce qu'il est vu par `resolve_log_level(None)` — le niveau de boot devient alors DEBUG et le handler est installe a DEBUG. Un developpeur qui verifie « est-ce que le mode debug marche ? » obtient donc toujours oui.

**Correctif** : `log_scrubber.set_rotating_log_level(level)`, appelee aux deux chemins juste apres le `setLevel` du root. `resolve_log_level` n'est pas modifiee : la priorite `CINESORT_LOG_LEVEL` > `CINESORT_DEBUG` > settings reste entierement la sienne.

## A2 — Le mode BUREAU n'installe aucun anti-spam d'exceptions repetees *(sev. 2)*

**Persona** : RELIABILITY · **Categorie** 14 (error handling) · **Confiance** 0,95

`install_repeated_exception_dedup` (Vague H, 2026-05-25) n'avait qu'un appelant : `main_api`. **`app.py:main` — le mode de l'EXE distribue, et le seul emprunte quand l'interface est la — ne l'appelait pas**, alors que la docstring de la fonction prescrit mot pour mot « a appeler une fois au boot dans **app.py:main / app.py:main_api** ».

Motif deja paye plusieurs fois ici : une garde generalisee a N-1 sites, **declaree complete par un commentaire du depot**.

Consequence : une exception en boucle — un thread de fond qui echoue a chaque cycle — ecrit sans limite dans `cinesort.log` et **fait tourner la rotation** (50 Mo x 5), donc efface les logs utiles. C'est precisement ce que la Vague H voulait empecher, et cela frappe le mode ou le diagnostic est le plus difficile.

## A3 — La surveillance auto des dossiers ne demarre jamais au boot du mode `--api` *(sev. 2)*

**Persona** : RELIABILITY · **Categorie** 19 · **Confiance** 0,90 · **SANS PR, et la raison compte**

`_start_watcher` a **un seul appelant** : `app.py:1180`, dans `_startup`, donc le mode bureau. `main_api` ne l'appelle jamais — pas plus que `_check_updates_in_background`.

Ce n'est pas une omission neutre : `main_api` arme deja les **deux crons destructifs** (retention, TTL quarantaine) et la purge du cache TMDb. L'intention « ce mode arme les taches de fond » est donc etablie ; le watcher en est le seul absent. Et c'est le mode qui tourne en permanence — celui ou une surveillance a le plus de sens.

**Rattrapage partiel, et il faut le dire** : `_sync_watcher` (`cinesort_api.py:990`) arme le watcher a chaque `save_settings`. En mode `--api`, la surveillance demarre donc — mais seulement si l'utilisateur retourne dans Parametres et re-enregistre. Le comportement n'est pas « inerte », il est **imprevisible**.

**Pourquoi pas de PR** : armer une surveillance qui declenche des scans automatiques dans un mode qui ne le faisait pas est un changement de comportement observable, donc un arbitrage produit — pas un correctif sur. Meme arbitrage que celui rendu le 10/09 sur le finding voisin A2 de ce module.

## A4 — Le court-circuit qui fige la portee d'un filtre *(sev. 1)*

**Persona** : RELIABILITY · **Categorie** 10 · **Confiance** 0,85

Un filtre pose sur un **LOGGER** ne s'applique pas aux records propages depuis un logger enfant : seuls les filtres de **HANDLER** le font. Le depot le sait et l'a ecrit deux fois — `log_scrubber.py:221-226` (motif du correctif AUDIT 2026-06-10, qui a retire ce meme court-circuit de `install_global_scrubber`) et `log_context.attach_filter_to_handler`.

**Mesure** : **0 occurrence** d'appel de log porte directement par le module `logging` dans `cinesort/` et `app.py`. Un filtre pose sur le root logger seul ne verrait donc **aucun** record de l'application.

La portee du garde etait par consequent decidee par le PREMIER appel. **Aucun defaut observable n'en decoulait** (cf. la rectification ci-dessous) : c'est de la defense en profondeur, et la PR le presente comme tel.

## La rectification du jour — `main_api` n'est pas un point d'entree autonome

Ce paragraphe est la partie la plus utile de ce rapport.

Ma premiere redaction de A2 affirmait : « l'anti-spam n'etait attache a **aucun** handler, parce que `main_api` l'appelait avant `basicConfig` et `install_rotating_log` ». Le correctif etait deja committe et la PR ouverte quand la verification adverse a tranche.

**C'est faux.** `app.py:1341` ne connait qu'un point d'entree, `main()`. Celui-ci cree les handlers (`basicConfig` 843, `install_rotating_log` 851), prend l'`InstanceLock`, **puis** dispatche vers `main_api()` a la ligne 890. Quand `main_api` installait le filtre, les handlers existaient donc depuis longtemps — le mode `--api` etait couvert.

Il l'etait par **coincidence** : la portee du garde dependait de l'ordre d'un AUTRE point d'entree. Cela reste une fragilite reelle, mais ce n'est pas le defaut que j'avais ecrit.

**Ce qui l'a revele** : avoir cherche, dans un tout autre but, si `main_api` prenait le verrou mono-instance. La reponse (il en herite, ligne 877 < 890) a du meme coup invalide ma lecture de `main_api` comme entree autonome.

**Ce qui aurait du le reveler plus tot** : lire le dispatch avant d'ecrire sur un « chemin de boot ». J'ai lu deux fonctions en parallele en supposant qu'elles etaient paralleles a l'execution. Elles sont **emboitees**.

Le recit a ete corrige dans le commit `47d50a5` (docstrings, commentaires, docstring du test) et dans le corps de la PR, l'erreur y restant visible plutot que reecrite. Le correctif, lui, tient entierement : A1 est intact dans les deux modes, et A2 — le mode bureau sans anti-spam — n'est pas touche par la rectification.

**Effet secondaire utile** : la meme lecture a fait tomber deux findings que j'allais ouvrir (cf. « Ecarte »).
