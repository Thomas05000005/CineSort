## Contrainte d'execution a connaitre pour lire ce rapport

Le runner de cet audit tourne en **sandbox sans execution Python** : `python3 -c`,
`python -m pytest`, `pip` et `uvx ruff` y sont tous refuses par la politique de
permissions. Aucune mesure dynamique n'a donc pu etre faite ce jour-la.

Consequence assumee, et ecrite ici pour que personne ne la deduise a tort :

- **les findings de ce rapport sont etablis par LECTURE**, assertion par assertion,
  pas par execution ;
- **les tests ajoutes par la PR n'ont pas ete vus ROUGES par moi**. La regle du
  CLAUDE.md (« un correctif n'est prouve que si le test a ete vu ROUGE sans lui »)
  n'a pas pu etre honoree localement. Chaque test porte dans sa docstring la
  valeur exacte que l'ancien code rendait, derivee a la main ; la CI est la
  barriere.

Meme cause, meme franchise pour le fichier de findings : les `id` de
`docs/internal/audits/findings/2026-08-15-all.jsonl` sont des **slugs lisibles**
(`a15sim01`, ...), **pas** les prefixes `sha256(module+line+symbol+category)[:8]`
que le schema demande — je ne pouvais pas les calculer. Ils restent stables et
uniques pour la dedup manuelle, mais ils ne se comparent pas aux `id` des
fichiers precedents.

C'est une limite de l'environnement, pas un raccourci de methode. Une execution
ulterieure de l'audit dans un runner autorisant Python devrait re-jouer la
verification ROUGE/VERT sur `tests/test_quality_simulator.py`.

## Findings en confiance basse (< 0.70) — PAS d'issue, consignes pour memoire

1. **`custom_rules` : les operateurs negatifs matchent sur un champ ABSENT.**
   `_op_ne(None, "dts")` rend True, idem `not_in` et `not_contains`. Une regle
   « `has_dv != true` -> `cap_max 70` » frappe donc aussi les films dont la sonde
   HDR a echoue. C'est le symetrique de #923 (« une analyse qui ECHOUE produit un
   score flatteur »), mais c'est defendable comme choix de conception : je n'ai
   trouve aucune trace ecrite d'un arbitrage dans un sens ou dans l'autre.
   Confiance ~0.60 — demande un arbitrage produit, pas un correctif.
2. **`_act_score_mult` accepte un facteur `0`.** Le film tombe a 0, donc Reject,
   sans le refus ni le message que #723 a poses pour les facteurs negatifs. Un `0`
   est peut-etre une intention legitime (« annuler ce film »). Confiance ~0.55.
3. **`plugin_hooks` : un `.bat` dont le NOM contient `&`.** `list2cmdline` ne
   quote que sur espaces/guillemets, donc `&` resterait un separateur pour
   `cmd.exe`. Portee reelle : les plugins sont des fichiers que l'utilisateur pose
   lui-meme sur sa propre machine — il a deja l'execution. Confiance ~0.50.
4. **`runtime_matching._EXTENDED_EDITIONS` contient `"directors cut"`** (sans
   apostrophe), forme que `edition_helpers._canonicalize` ne produit jamais — il
   rend toujours `"Director's Cut"`. Entree morte, strictement inoffensive
   (defense pour un appelant qui passerait du brut). Severite 0.

des 13 et 14 aout : le rendement de l'audit **baisse**, et c'est le signe
attendu. Les balayages mecaniques (categories 1, 3, 5, 12, 14, 15) ne rendent

Les deux findings du jour sont d'ailleurs la **meme forme** que ceux des trois
campagnes precedentes : une valeur ou une regle re-ecrite a cote de celle qui
fait autorite. Le depot a deja paye cette cause quatre fois, et sa formulation la
plus juste est celle de `tests/test_poids_profil_qualite_ecran.py` :

> Une constante qui fait autorite a la place du backend finit toujours par
> diverger.

La piste la plus rentable pour un prochain run n'est donc pas un nouveau motif de
`grep`, mais un **inventaire des re-implementations** : chercher, pour chaque
helper du domaine qui porte une regle metier (`determine_tier`, `normalize_tiers`,
`classify_resolution`, `confidence_thresholds`), tous les endroits qui refont son
travail au lieu de l'appeler. `resolution_class.py` en documente d'ailleurs quatre
en reserve assumee.
