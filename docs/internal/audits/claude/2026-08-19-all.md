## A1 — BUG : le codec PCM/LPCM n'est classé dans aucune table de rang audio

**Persona** : RELIABILITY. **Catégorie** 2 (bug domaine) + 19 (cohérence). **Confiance** 0,95.
**Corrigé — PR #1114.**

`cinesort/domain/codec_ranks.py` porte les deux tables de rang audio du dépôt :

| Table | Lookup | Consommateurs |
|---|---|---|
| `AUDIO_CODEC_RANK` | exact | `quality_score._audio_codec_rank`, `duplicate_compare._audio_codec_rank_value` |
| `AUDIO_CODEC_RANK_PATTERNS` | substring | `audio_analysis._classify_codec`, `perceptual/audio_perceptual.select_best_audio_track` |

Aucune des deux n'avait d'entrée PCM. Toute piste PCM tombait donc au rang **0**, soit **sous le
MP3 et l'AAC** (rang 1). Trois conséquences, toutes atteignables en configuration **nominale**
(ffprobe, `probe_backend = auto`) :

1. **La mauvaise piste est élue.** `_best_audio_track` trie sur `(rang_codec, canaux, débit)` :
   sur un remux dont la piste principale est du LPCM 5.1 et qui porte une piste AAC 2.0
   secondaire, l'AAC (rang 1) passe devant le LPCM (rang 0). Tout le sous-score audio est ensuite
   calculé sur cette piste-là.
2. **Le comparateur de doublons perd le critère « Audio codec » (poids 15).** Le fichier PCM
   affiche `?` (`_audio_codec_label(0)`) et cède 15 points à n'importe quel AAC. Or ce comparateur
   désigne le gagnant que **« Auto-décider tous »** applique — le perdant est archivé.
3. **Le badge audio retombe sur `_TIER_MAP[0]`, soit « bronze »**, avec le libellé « Inconnu ».

**Le dépôt se contredisait lui-même** : `release_name_parser._PATTERNS_AUDIO:146` déclare
`(r"\bPCM\b|\bLPCM\b", "pcm", True)` — le dernier champ est `lossless` — et
`quality_score._NAME_AUDIO_CODEC_TO_PROBE["pcm"] = "pcm"` (l. 2038). **Le fallback par le NOM
fabriquait donc lui-même une étiquette qu'aucune table ne savait lire.** Le cas ne dépend d'aucun
backend exotique : ffprobe rend `pcm_s16le` / `pcm_s24le` / `pcm_bluray` / `pcm_dvd`.

Correctif borné : `"pcm": 3` (le rang de FLAC, l'autre lossless de ces tables — ce n'est pas un
arbitrage nouveau) et normalisation des variantes dans `_canonical_audio_codec`.
`_audio_codec_bonus` et `_is_premium_multichannel_codec` rendent **exactement la même valeur
qu'avant** : les faire bouger demanderait une clé de profil (cf. A3).

## A2 — BUG : en `probe_backend = "mediainfo"`, trois étiquettes audio sont inatteignables

**Persona** : RELIABILITY. **Catégorie** 2 + 11 (code mort). **Confiance** 0,90. **Non corrigé.**

`quality_score._canonical_audio_codec` dérive l'étiquette canonique d'une piste depuis **trois**
champs, et trois seulement : `profile`, `is_atmos`, `is_dts_x`. C'est explicite dans sa docstring —
« ffprobe range le codec de base dans `codec` et la variante dans des champs SÉPARÉS ».

Or `infra/probe/_normalize_mediainfo.py:94-104` ne produit, pour une piste audio, que :
`index`, `codec`, `channels`, `language`, `bitrate`, `title`, `is_commentary`. **Ni `profile`, ni
`is_atmos`, ni `is_dts_x`** — ces trois champs ne sont produits **que** par la branche ffprobe
(`_normalize_ffprobe.py:212-230`, qui appelle `_detect_atmos_dtsx`).

Et `_normalize_merge._merge_probes:185-192` ne fusionne pas les deux listes : il **choisit**
(`if ff_audio: … elif mi_audio: …`). En `backend == "mediainfo"`, `service.py:579-588` n'appelle que
`run_mediainfo_json`, donc `raw_ffprobe is None` et la liste retenue est celle de MediaInfo.

**Conséquence démontrable par lecture pure, sans exécuter MediaInfo :** dans ce mode, les étiquettes
`truehd atmos`, `dts-hd ma`, `dts-hd hra` et `dts:x` ne peuvent **jamais** être produites. Donc :

- `_hierarchy_audio_codec_token` ne peut jamais rendre `truehd_atmos` ni `dts_x` → les deux
  planchers de `DEFAULT_HIERARCHY_AUDIO_FLOORS` sont **du code mort dans ce mode** ;
- `_audio_codec_bonus` ne peut jamais rendre « Audio DTS-HD MA » (+10) ni « Audio DTS:X » : un
  remux DTS-HD MA est scoré comme un DTS lossy (+6) ;
- le comparateur de doublons ne distingue plus un remux lossless d'un WEB-DL.

**Le chemin est atteignable** : `probe_backend` est un `<select>` de l'écran Paramètres > Analyse >
Probe (`web/dashboard/views/parametres.js:75-77`, options `auto / ffprobe / mediainfo / none`), et
`settings_support.normalize_probe_backend` accepte les quatre.

**Ce que je n'ai PAS pu mesurer ici** (le runner n'exécute rien) : les valeurs exactes que MediaInfo
écrit dans `Format`. Deux indices internes au dépôt suggèrent que le problème est plus large que
les seules variantes — `perceptual/composite_score_v2.py:626` liste `"mlp"` parmi les codecs
lossless (c'est le `Format` MediaInfo du TrueHD), et `_AUDIO_CANONICAL_RANK_ALIAS` porte déjà les
formes hyphénées `ac-3` / `e-ac-3` **en citant nommément `_normalize_mediainfo`**. Ni `"mlp"` ni
`"pcm"` ne sont des clés de `AUDIO_CODEC_RANK`.

**Pourquoi pas de PR** : le correctif consiste à enrichir `_extract_mediainfo` depuis
`Format_Commercial_IfAny` / `Format_AdditionalFeatures`. Je ne peux pas vérifier ces noms de champs
sur ce runner, et un test forgé à partir d'un JSON que j'aurais inventé validerait **mon harnais,
pas la production** — exactement le piège documenté dans `/CLAUDE.md` (« le HARNAIS ne reproduisait
pas la production »). Il faut une sortie MediaInfo réelle comme fixture.

## A3 — QUALITY : `_audio_codec_bonus` ne connaît que quatre codecs

**Persona** : RELIABILITY. **Catégorie** 2 + 19. **Confiance** 0,90. **Non corrigé.**

`quality_score._audio_codec_bonus:904-948` teste, dans l'ordre : `truehd`, `atmos`, `dts…hra`,
`dts-hd`/`dtsx`, `dts`, `aac`. Puis `return 0, ""`. Les clés du profil sont
`truehd_atmos_bonus` (12), `dts_hd_ma_bonus` (10), `dts_bonus` (6), `aac_bonus` (3) — il n'existe
**aucune** clé pour AC-3, E-AC-3, FLAC, PCM, MP3 ni Opus.

Résultat, à canaux et débit égaux :

| Codec | Rang `AUDIO_CODEC_RANK` | Bonus `_audio_codec_bonus` |
|---|---|---|
| FLAC | 3 | **0** |
| PCM | (0 avant #1114, 3 après) | **0** |
| E-AC-3 | 2 | **0** |
| AC-3 | 2 | **0** |
| AAC | **1** | **+3** |

**Le seul codec récompensé est le moins bon des cinq.** Sur un scénario nominal — AC-3 5.1 à
640 kbps (107 kbps/canal, donc −3 « débit faible ») contre AAC 5.1 à 384 kbps (64 kbps/canal,
−3 également) — l'AAC finit **3 points au-dessus** de l'AC-3, alors que les deux tables de
`codec_ranks` et `release_name_parser` le classent en dessous.

Le débit par canal compense partiellement pour FLAC et PCM (+4 « débit audio élevé »), mais pas
pour AC-3/E-AC-3, et le compteur n'émet **aucune raison** : l'écran « Explication du score »
n'affiche rien pour ces cinq codecs.

**Pourquoi pas de PR** : ajouter `flac_bonus` / `ac3_bonus` / `pcm_bonus` étend le **schéma de
profil utilisateur**, donc touche `validate_quality_profile`, les presets embarqués, l'import/export
Recyclarr et le simulateur. C'est un arbitrage produit (quelle valeur ?), hors périmètre « modéré »,
et `/CLAUDE.md` documente déjà ce qu'une garde posée au mauvais point de passage a coûté (#1083).

## A4 — LOW-CONFIDENCE : le seuil ms/s de MediaInfo bascule à 100 secondes

**Persona** : RELIABILITY. **Confiance** 0,55 → consigné dans le `.jsonl`, **sans issue**.

`infra/probe/_normalize_helpers._duration_seconds_from_mediainfo` :

```python
if v > 100000.0:
    return round(v / 1000.0, 3)   # interprété comme des millisecondes
return round(v, 3)                # interprété comme des secondes
```

Le point de bascule est 100 000 ms = **100 secondes**. Si MediaInfo rend des millisecondes pour un
média court (sample de release, bonus, générique), la valeur est lue comme des secondes :
60 000 ms → **60 000 s**, soit 16 h 40. Je n'ai pas pu mesurer l'unité réelle de `general.Duration`
sur ce runner ; la sortie JSON de MediaInfo est réputée être en secondes décimales, auquel cas
l'heuristique ne se déclenche jamais et le code est simplement mort. D'où la confiance basse.
