## Signale sans PR — la raison compte autant que le constat

### A2 — `_PATTERNS_AUDIO` : le finding tient toujours, et son remede ecrit introduirait une REGRESSION *(sev. 3)*

Le finding `f7f34a19` (2026-08-20) est **encore vrai sur `main`** : la frontiere
`\b` en queue des motifs audio ne peut pas matcher devant un chiffre, donc les
formes collees — les plus repandues sur le web — perdent leur codec porteur.

```
AAC2.0      -> \bAAC\b     : 'C' puis '2', deux caracteres de MOT -> aucune frontiere -> AUCUN match
FLAC2.0     -> idem
DTS5.1      -> idem
TrueHD7.1   -> idem
DTS-HD.MA5.1 -> le motif MA echoue ; \bDTS-?HD\b matche -> degrade en dts_hd LOSSY
DD5.1 / DDP5.1 -> matchent, parce que leurs motifs portent un [0-9]? qui absorbe le chiffre
```

**La mesure NOUVELLE de ce run, et c'est elle qui compte** : le `fix_suggestion`
enregistre avec le finding disait *« remplacer le `\b` de queue par
`(?![A-Za-z])` sur les motifs concernes »*. Applique en bloc, il **casse le
motif DTS:X** :

```
"...BluRay DTS X264-GROUP"
  aujourd'hui  : \bDTS[: \-]?X\b  -> 'X' puis '2' : pas de frontiere -> PAS de match (correct)
  avec (?![A-Za-z]) : 'X' puis '2' : '2' n'est pas une lettre -> MATCH -> audio_is_dts_x = True
```

Or `re.search(..., re.IGNORECASE)` (`_parse_audio_hints`) et le separateur
optionnel `[: \-]?` avalent l'espace : un **DTS lossy ordinaire** serait promu
DTS:X, donc `dts-hd ma` LOSSLESS via `_AUDIO_CANONICAL_RANK_ALIAS`. Le remede
serait plus couteux que le defaut.

**Le remede SUR** se decompose donc :

- widening a `(?![A-Za-z_])` — qui n'admet que les CHIFFRES, `_` restant exclu —
  sur `Atmos`, `DTS-HD MA`, `DTS-HD HRA`, `DTS-HD`, `TrueHD`, `FLAC`, `PCM`,
  `LPCM`, `DTS`, `AAC` ;
- **ne PAS y toucher pour `DTS[: \-]?X`**, dont le separateur optionnel rend le
  widening dangereux ;
- l'argument de surete est une inclusion : `\b` en fin de token exige un
  caractere NON-MOT, `(?![A-Za-z_])` exige un caractere non-lettre et non-`_` ;
  tout non-mot etant non-lettre, le nouveau jeu de matches est un **sur-ensemble
  strict**, et l'elargissement est de plus MONOTONE vers le codec le plus riche
  (la boucle parcourt la liste du plus riche au plus pauvre et garde le premier).

**Pas de PR** : le run du 08-20 avait deja refuse ce correctif au niveau modere
(« dix motifs a la fois dans le parser qui score chaque film, sans batterie
executable sur ce runner »), et ce refus tient. Je n'apporte pas une raison de
l'annuler — j'apporte la raison de **ne pas l'appliquer tel qu'il etait ecrit**.

### A3 — `scope="validated"` elargit au lieu de refuser *(sev. 2, atteignabilite NON demontree)*

`quality_support._resolve_ids_from_scope` :

```python
try:
    val_payload = api.run.load_validation(run_id)
except (AttributeError, OSError, TypeError, ValueError):
    val_payload = None
validated_ids = _extract_validated_ids(val_payload)   # -> None
...
if validated_ids is not None and rid not in validated_ids:
    continue                                          # filtre SAUTE
```

`_extract_validated_ids` rend `None` dans **trois** cas — payload absent,
`ok: False`, `decisions` non-dict — et l'appelant lit ce `None` comme « pas de
filtre ». « Je n'ai pas pu lire les validations » devient donc « analyse tout »,
sur un chemin qui lance un `ffprobe` par film (jusqu'a 300 s chacun).

**Je n'ai PAS trouve de scenario atteignable, et je le dis** :
`load_validation` ne rend `ok: False` que sur « Run introuvable », que
`api.run.get_plan(run_id)` — appele juste avant — aurait deja intercepte ; et
`PlanCorruptedError` derive de `ValueError` (donc bien capturee), mais le plan
corrompu fait echouer `get_plan` en amont.

La forme reste fausse, et c'est la seule des trois branches qui **elargit** au
lieu de refuser. Remede restrictif en 4 lignes : distinguer « aucune validation »
(ensemble vide, filtre applique, resultat vide) de « validations illisibles »
(refus explicite).

### A4 — six alternances de `_TITLE_NOISE_RE` sont MORTES par construction *(sev. 1)*

`mkv_title_check._title_tokens` remplace `[._\-]+` par une espace **avant**
d'appliquer `_TITLE_NOISE_RE`. Tous les motifs de bruit qui portent un
separateur interne ne peuvent donc plus jamais matcher :

| Motif declare | Chaine reellement vue | Match ? |
|---|---|---|
| `blu-ray` | `blu ray` | non |
| `web-?dl` | `web dl` | non |
| `web-?rip` | `web rip` | non |
| `h\.?264` | `h 264` | non |
| `h\.?265` | `h 265` | non |
| `dts-hd` | `dts hd` | non (`dts` matche seul, `hd` survit) |

Consequence mesurable : un titre de conteneur fait **uniquement** de tags
techniques a tirets produit un faux `mkv_title_mismatch`, alors que le meme
contenu ecrit avec des points ne le produit pas — c'est exactement ce que
`test_container_title_made_only_of_technical_noise_is_not_a_conflict` existe
pour empecher, et la forme a tirets lui echappe.

Impact borne : `mkv_title_mismatch` n'est **pas** dans `_AUTO_BLOCKING`, il ne
bloque donc pas l'auto-approbation ; c'est une alerte affichee de trop.

**Piege du remede, releve ici pour la meme raison qu'en A2** : l'alternance
liste `dts` AVANT `dts-hd`. Rendre les separateurs flexibles sans reordonner
laisserait `dts` gagner et `hd` survivre.

**Pas de PR** : c'est une famille de regex, et ce depot porte la cicatrice d'une
famille de regex iteree plutot qu'abandonnee. Le gain (une alerte cosmetique en
moins) ne justifie pas le risque au niveau modere.
