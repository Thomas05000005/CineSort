## Corriges (PR ouvertes)

### #1133 — `fix(rel)` : « 0 = desactive » est promis a l'ecran, et avale avant le cron — **severite 4**

Cinq endroits promettent le comportement correct :

1. l'ecran Parametres, **a l'utilisateur** : `min: 0`, hint « 0 = désactivé »
   (`web/dashboard/views/parametres.js:363`) ;
2. le commentaire du meme ecran (`:360`) : « `quarantaine_ttl_days = 0`
   desactive le cron » ;
3. le validateur backend : borne `[0, 3650]`, commentaire « 0 = OFF » — et il
   fait un `to_int`, donc il **persiste un entier `0`**, precisement la valeur
   qui declenche le defaut ;
4. les deux demarreurs : `if days <= 0: return None` ;
5. les commentaires d'`app.py`, **une ligne au-dessus** du `or` qui les annule.

Un seul chemin les relie, quatre fois (deux crons x deux modes de boot) :

```python
int(settings.get("quarantaine_ttl_days") or _Q_DEFAULT_TTL)   # 0 or 30 -> 30
int(settings.get("history_retention_days") or 90)             # 0 or 90 -> 90
```

Mesure sur la ligne de production :

```
pose=None -> recu=30       pose=0  -> recu=30   <-- desactive, purge quand meme
pose=''   -> recu=30       pose=45 -> recu=45
```

**Ce que la batterie existante ne pouvait pas voir.**
`tests/test_quarantaine_ttl_v77.py:319` appelle **deja**
`start_quarantine_ttl_cron(api, ttl_days=0)` et verifie qu'il rend `None`. Ce
test est reste **vert pendant tout le defaut**, parce qu'il passe le zero
lui-meme : il eprouve la DECISION, pas le SITE D'APPEL. C'est le piege que
`/CLAUDE.md` documente mot pour mot. Chercher le garde avant d'en ecrire un a
paye : il ne fallait pas doubler ce test, il fallait couvrir son angle mort.

Le cliquet ajoute vise donc `app.py` par AST, avec sa contre-epreuve (sans
elle, « 0 site fautif » serait satisfait par un fichier vide). Cycle
vert → rouge → restaure → vert **execute**, mutation en binaire, compteur
d'occurrences verifie : 4 sites mutes, 3 assertions rouges.

### #1132 — `fix(rel)` : le repli relatif de #1074 subsistait sur 9 sites qui le reimplementent — **severite 3**

#1074 a rendu ABSOLU le repli de `state.default_state_dir()` : il valait `"."`,
donc `./CineSort`. Le correctif a ete pose dans la fonction canonique, et son
garde (`tests/test_state_dir_repli_absolu.py`) ne l'eprouve **que la**.

```
'default_state_dir' dans app.py : 0 occurrence(s)
'LOCALAPPDATA'      dans app.py : 8 occurrence(s)
```

**Neuf** sites reimplementent la resolution : 6 dans `app.py`, 2 dans
`cinesort_api.py`, 1 dans `reset_support.py`. Ils ne portent que **quatre
formes distinctes** ; la sonde a evalue une expression par forme, plus la
fonction canonique et `runtime_support._logs_dir` (qui a son propre repli),
soit **7 expressions**. Mesure, `LOCALAPPDATA` retire :

```
ABSOLU   default_state_dir()          -> /home/runner/CineSort
RELATIF  app.py:96                    -> CineSort
RELATIF  app.py:432                   -> CineSort/logs
RELATIF  app.py:676                   -> CineSort
RELATIF  cinesort_api.py:3127         -> CineSort/logs
RELATIF  cinesort_api.py:3154         -> CineSort/logs
RELATIF  reset_support.py:380         -> CineSort
ABSOLU   runtime_support.py:682       -> /home/runner/AppData/Local/CineSort/logs

-> 6 expressions sur 7 rendent un chemin RELATIF au repertoire de lancement.
```

Les trois sites d'`app.py` non listes ci-dessus (`604`, `1068`, `1114` :
`webview2_userdata`, `webview/EBWebView`, `webview/`) portent la meme forme que
`app.py:96` et rendent donc le meme chemin relatif.

`runtime_support` est le seul a avoir un repli **absolu** — mais il diverge de
celui de `default_state_dir()` (`~/AppData/Local/CineSort` contre `~/CineSort`),
ce qui est le second defaut ci-dessous.

Deux consequences, pas seulement un chemin inelegant :

- **le verrou anti-double-instance ne garde plus la base qu'il protege.**
  `app.py:698` donne ce chemin a `InstanceLock`, alors que `CineSortApi` ouvre
  la base sur `default_state_dir()` (absolu, `cinesort_api.py:278`). Deux
  lancements depuis deux repertoires prennent **deux verrous distincts sur une
  base commune** — exactement la corruption que le commentaire du site dit
  empecher ;
- **un `rmtree` a racine variable** : `app.py:1068` passe ce chemin a
  `_shutil.rmtree` (purge du cache WebView2).

Et le journal partait dans `./CineSort/logs` tandis que la visionneuse
(`runtime_support._logs_dir`) lisait `~/AppData/Local/CineSort/logs` : deux
replis **absolus mais divergents**, donc un ecran de logs vide.

**Portee honnete** : `reset_support.py:380` est de la duplication, **pas un
defaut atteignable** — en production `_resolve_state_dir` rend toujours
l'absolu, le repli ne servait qu'aux fakes de tests. Corrige par coherence.

Le garde est **etendu, pas double** : un cliquet AST — pas un grep, une mention
en docstring est legitime — avec trois exemptions justifiees dans le test
(`infra/state.py`, `probe/tools_manager.py` qui vise WinGet et porte deja sa
garde, `app/plugin_hooks.py` ou `LOCALAPPDATA` est une entree de liste blanche
d'environnement, cf #1098).

## Findings VERIFIES mais SANS PR — et pourquoi

### `8dfa8aa5` — `_mirror_decisions_to_sql` jette le statut, et son repli est un no-op

`run_flow_support.py:1421` appelle `decisions_repo.set_decision(...)` en
**position d'instruction** : le retour est jete. Or `set_decision` signale ses
deux refus **par retour, pas par exception** — `film_id` vide, et `decision`
hors de `{accepted, rejected, deferred}`. Aucun log, aucun compteur : le miroir
tri-etat est perdu en silence.

Et le bloc `except` juste en dessous porte :

```python
    # On force malgre tout decision=DECISION_REJECTED pour eviter
    # le silence complet (ce code branch est defensif).
    _ = DECISION_REJECTED
```

`_ = DECISION_REJECTED` **ne force rien** : c'est une affectation morte. Le
commentaire decrit une action qui n'a pas lieu — famille de la « docstring qui
decrit l'INVERSE du code » (#1070-#1075).

**Pourquoi pas de PR** : la fonction est explicitement best-effort et le JSON
reste la source primaire, donc aucune decision utilisateur n'est perdue — seule
la table `film_decisions_v2` (historique long terme + filtre UI) perd sa ligne.
Le correctif est trivial (lire le retour, loguer, retirer le no-op) mais il
faut trancher si l'echec de miroir doit remonter quelque part ou rester muet :
c'est un choix, pas une reparation.

### `074e89a7` — `cleanup_old_runs` : `0` veut dire « 1 jour », et les echecs ne se comptent pas

Deux points sur `history_support.cleanup_old_runs` :

1. `days = max(1, int(retention_days or 0))`. Or `retention_cleanup.py:12-13`
   documente « pour desactiver la retention auto, passer `retention_days=0` ».
   La meme valeur veut donc dire « jamais » dans un module et « 1 jour » dans
   l'autre. Le cron est protege (`if days <= 0: return None` **avant** l'appel),
   mais la route REST `POST /api/run/cleanup_old_runs` avec
   `{"retention_days": 0, "dry_run": false}` supprime tout run de plus d'un jour.
2. le payload ne porte **aucun compteur d'echec**. `deleted_ids` n'est
   incremente qu'en cas de succes — il est donc HONNETE, contrairement a
   `purge_review_bucket_all` (#1062) — mais si 50 suppressions sur 100 echouent,
   la reponse dit `ok: True, deleted_count: 50` sans que rien ne signale les 50
   autres. Le cron loggue alors « deleted 50 runs ».

**Pourquoi pas de PR** : le point 1 demande de choisir la convention (0 = jamais,
ou 0 = interdit sur cette route) et touche une frontiere destructive ; le point 2
ajoute une cle au payload, or le depot vient d'ecrire un test entier
(`LeVerdictNAtteintAUCUNEcranTests`) pour constater qu'une cle posee sans lecteur
est un silence de plus. Les deux sont des arbitrages.

### `a7721f36` — les breakers mesurent des durees a l'horloge murale

`_circuit_breaker.py:129/159/171`, `probe/_source_circuit_breaker.py` (4 sites)
et `probe/disk_cache.py` (2 sites) comparent `time.time()` a un `_open_until`
calcule par `time.time() + recovery_timeout`. Un recul d'horloge (ajustement
NTP, changement d'heure, sortie de veille) laisse le circuit ouvert plus
longtemps que son `recovery_timeout` ; une avance le ferme trop tot.

`run_id.py` traite deja explicitement ce cas pour les identifiants
(`_MonotonicSlots` documente « horloge RECULEE ») et `probe/service.py:244`
utilise `time.monotonic()` : le depot connait la distinction, elle n'a
simplement pas ete appliquee ici.

**Pourquoi pas de PR** : severite 1 (degradation temporaire d'une integration,
rien de destructif), et `_open_until` est un etat partage entre threads dont le
passage en `monotonic` demande de verifier chaque lecteur — dont
`is_open`, expose. Disproportionne pour le gain.

Mesure AST sur tout `cinesort/` : **66** parametres ne sont references nulle

  Les six appels de la suite de tests passent `None`.

**Pourquoi pas de PR** : ce sont des signatures, pas des comportements. Les

## Un point de methode

**La sonde qui a trouve #1133 n'est pas celle qui l'a cherchee.** Elle est
sortie d'une mesure des « valeurs par defaut divergentes pour un meme reglage »
(la famille de #1080), qui n'a rendu qu'**un seul** resultat — et un resultat
hors sujet, sur `os.environ.get("LOCALAPPDATA", ...)`. C'est en allant verifier
ce faux positif dans `reset_support.py` que la famille du repli relatif
(#1132) est apparue, puis, en tirant le fil de `retention_cleanup.py`, celle du
zero avale (#1133).

Deux sondes a zero resultat utile ont donc produit les deux findings du jour.
Ce qui a paye n'est pas la sonde mais **la verification systematique de chaque
faux positif dans le code** — la ou la tentation est de les ecarter en lot.
