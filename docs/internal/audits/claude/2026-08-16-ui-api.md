### A1 — la reecriture de plan qui efface son propre temoin (corrige, PR)

`cinesort/ui/api/library_actions_support.py:706` (`_rematch_tmdb_and_update_plan`)
et `cinesort/ui/api/tmdb_support.py:209` (`enrich_tmdb_ids_by_title`) relisent
`plan.jsonl` ligne par ligne, **sautent silencieusement** toute ligne illisible
(`except (TypeError, ValueError): continue`, plus `if not isinstance(data, dict):
continue`), puis appellent `run_data_support.write_plan_jsonl(plan_jsonl,
all_rows)` — qui **reecrit le fichier ENTIER**. La ligne fautive disparait donc
du plan, definitivement.

C'est exactement la politique que l'issue #519 a rejetee, et pour la raison
qu'elle nomme : `plan.jsonl` est le fichier que l'APPLY relit pour renommer et
DEPLACER des dossiers de films.

Ce qui rend la perte grave, c'est qu'elle **efface aussi son propre temoin** :

    avant la reecriture : load_rows_from_plan_jsonl leve PlanCorruptedError
                          -> l'apply refuse et dit « Plan corrompu: 1 ligne(s)
                             illisible(s) (ligne 42) sur 854 entree(s) »
    apres la reecriture : le plan est syntaxiquement PARFAIT, plus rien ne
                          rougit, l'apply s'execute sur N-1 films avec
                          `errors: 0` — un succes franc. Le film reste en
                          place et personne ne peut le savoir.

**Atteignabilite verifiee, pas supposee.** Le doute legitime etait : « le
chemin de re-scan ne s'arrete-t-il pas AVANT, sur le plan corrompu ? ». Non.
`_rescan_single_row_full_pipeline` appelle d'abord `run_flow_support.rescan_row`,
dont les trois etapes avalent chacune l'echec (`get_quality_report` a un
`except Exception` global, `get_perceptual_report` aussi, et `get_plan` rend
`{ok: False}` sans lever) — puis `rescan_row` rend **`ok: True`** (c'est le
finding A3), donc le pipeline continue jusqu'a `_rematch_tmdb_and_update_plan`.
Cote `enrich_tmdb_ids_by_title`, la fonction est atteignable en REST
(`POST /api/integrations/enrich_tmdb_ids_by_title`) sur n'importe quel run.

**Verification adversaire.** Trois raisons pour lesquelles ce finding aurait pu
etre faux, toutes cherchees dans le code :

1. *« C'est deja corrige. »* Non : les deux `continue` muets sont sur `main` au
   SHA `90c4938`, et `write_plan_jsonl` est appele inconditionnellement apres.
2. *« La garde existe ailleurs. »* Cherche. `tests/test_lectures_fragiles_519_492_508.py`
   porte bien l'invariant #519 — mais uniquement sur les trois chemins de
   **LECTURE** (`load_rows_from_plan_jsonl`, `count_plan_rows`, l'apply). Aucun
   test ne couvre les deux chemins de **REECRITURE** : `grep -rln
   "PlanCorruptedError" tests/` ne rend que ce fichier.
3. *« Le chemin est inatteignable. »* Refute ci-dessus, par lecture du flux
   complet.

**Correctif** : un helper partage `run_data_support.read_plan_rows_as_dicts`,
jumeau exact de `load_rows_from_plan_jsonl` (meme politique fail-closed, meme
lecture BINAIRE pour compter les octets non-UTF-8, meme parcours complet avant
de lever) mais rendant les dicts bruts dont les deux reecrivains ont besoin.
Sur plan corrompu : `enrich_tmdb_ids_by_title` refuse avec un message qui NOMME
la perte, `_rematch_tmdb_and_update_plan` rend `None` — son contrat de repli
deja en place — et **le fichier n'est pas touche**.

### A2 — un run utilitaire pris pour le dernier scan

`cinesort/ui/api/film_support.py:43` resout « le dernier run » par
`store.run.list_runs(limit=1)`. Ses deux jumeaux ont corrige ce defaut et
disent pourquoi, mot pour mot :

    library_audit_support.py:35  « l'ancien list_runs(limit=1) prenait le run
    quality_audit_support.py:37    utilitaire d'un bulk Re-scanner (sans plan)
                                   => '0 films' sur la vue »

Tous deux delèguent desormais a `library_support._resolve_run_id`, qui saute les
runs marques `rescan_run_id`. `film_support` a ete oublie. Consequence : apres
un `rescan_rows_bulk`, ouvrir une fiche film **sans run_id explicite** resout le
run de tracking (qui n'a pas de plan) et rend « Film introuvable ». Le cas est
reel : `film-detail.js:105` n'ajoute `run_id` que s'il en a un (`if (runId)
params.run_id = runId`), or la route standalone `/film/:id` n'en fournit pas.

Non corrige dans cette PR : le remede touche a la topologie d'imports
(`film_support` -> `library_support` alors que `library_support` importe deja
`film_support` en differe, avec une note qui mesure le cout d'un changement
d'arete — cf. `library_support.py:500-508`). Cela demande une mesure du graphe
d'imports que ce runner ne peut pas faire (il n'execute rien). Decrit en issue.

### A3 — `rescan_row` annonce un succes quand tout a echoue

`cinesort/ui/api/run_flow_support.py:2117`. Les trois etapes (invalidation de
cache, `get_quality_report`, `get_perceptual_report`) sont chacune enveloppees
dans un `try/except` qui journalise et continue, et la quatrieme
(`api.run.get_plan`) ne leve pas non plus. Le retour final est
`{"ok": True, ...}` **inconditionnel**, avec `quality: {}`, `perceptual: {}` et
`plan_row: None`. C'est la famille « un echec devient un succes silencieux »
deja payee par #1062 et #1053.

### A4 — le simulateur de preset compare contre une baseline perimee

`cinesort/ui/api/quality_simulator_support.py:75`. La cle de cache est
`(run_id, preset_id, overrides, scope)`. Elle n'inclut **pas** le profil
BASELINE (`_get_active_profile`), alors que tout le rapport est un avant/apres
contre lui. Et `clear_cache()` n'a **qu'un seul appelant** :
`cinesort_api.py:2081`, dans `_apply_quality_preset_impl`. Ni
`_save_quality_profile_impl`, ni `_set_active_profile_impl`, ni
`_import_quality_profile_impl`, ni `_save_profile_impl` ne l'appellent (mesure :
`grep -n "_sim_clear" cinesort/ui/api/cinesort_api.py` rend deux lignes,
l'import et cet unique appel). Changer de profil actif par l'une de ces quatre
routes laisse donc le cache intact : la simulation suivante montre un « avant »
qui n'est plus le profil de l'utilisateur.

Second effet du meme defaut : `run_id` vaut litteralement `"latest"` dans la
cle. Apres un nouveau scan, la simulation ressert le rapport de l'ancien run.

### A5 — un seul candidat essaye la ou plusieurs sont offerts

`cinesort/ui/api/quality_internal_support.py:77`. La boucle
`for entree in _candidats_par_id(settings, pid):` contient un `return`
inconditionnel : elle n'essaie donc que le PREMIER candidat, et rend `None` s'il
est invalide, sans regarder les suivants. `_candidats_par_id` peut pourtant en
rendre plusieurs (plusieurs presets partageant un id). Cosmetique aujourd'hui,
mais la forme `for ... : return` dit une intention que le code ne tient pas.
