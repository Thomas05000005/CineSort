## Detail des findings retenus

### 1. quality_report_support.py:102 — scoring genre-aware mort (BUG, sev 3)

`_probe_and_score` (SEUL call site de production du scoring qualite) construisait le
client TMDb via :

```python
tmdb = api._tmdb_client() if hasattr(api, "_tmdb_client") else None
```

Or `CineSortApi` **n'a aucun attribut `_tmdb_client`** -> `hasattr` toujours `False`
-> `tmdb` toujours `None` -> `tmdb_genres` toujours `[]` -> tout le scoring
genre-aware (`_apply_era_bonuses` + regles custom sur genre, categorie P4.2) etait
**mort silencieusement en production**.

- **Racine** : le helper correct existe deja et est documente :
  `cinesort/ui/api/perceptual_support.py:1671` `_build_tmdb_client(api)` (le call site
  perceptuel l'utilise, marque `AUDIT 2026-06-10 (REAL 2/2)`). `_probe_and_score`
  n'avait jamais ete recable dessus.
- **Contraste** : `cinesort/ui/api/library_audit_support.py:227` utilise
  `getattr(api, "_tmdb_client", None)` MAIS gere le `None` avec un fallback correct
  qui reconstruit le client -> PAS un bug (verifie).
- **Fix (PR #761)** : import de `_build_tmdb_client` dans `quality_report_support`, et
  remplacement du call site par `tmdb = _build_tmdb_client(api)` (commente
  `AUDIT 2026-07-17`). Le two-pass `compute_quality_score` existant transmet desormais
  `tmdb_genres` aux DEUX passes.
- **Test** : classe `TmdbGenreScoringTests` ajoutee dans
  `tests/test_quality_score_amputation_h1_h2.py` — echoue avant le fix (mock
  `_build_tmdb_client` jamais appele), passe apres (genres transmis aux 2 passes).
- **Severite** : BUG (3) — feature entiere morte, mais degradation silencieuse (pas de
  crash, scoring toujours produit sans le bonus genre).
- **Action** : Issue #760 + PR #761 (branche `fix/audit-all-quality-report-tmdb-genres`,
  `Closes #760`).

### 2. title_ambiguity.py — incoherence de perimetre detection/desambiguisation (QUALITY, sev 2)

- `detect_title_ambiguity` (l.78-89) ne compte comme "ambigu" QUE les candidats issus
  de sources TMDb (`tmdb` / `nfo_tmdb` / `nfo_imdb`).
- `disambiguate_by_context` (l.170-186) booste ensuite N'IMPORTE QUEL candidat au
  `title_key` egal, **quelle que soit sa source**.
- Consequence : le perimetre de "ce qui est ambigu" et "ce qui est desambigue" diverge
  -> un candidat de source non-TMDb peut etre booste alors qu'il n'a jamais compte dans
  la detection. Pas un crash, mais une decision de scoring potentiellement incoherente.
- **Severite** : QUALITY (2), **needs-review** — le fix (aligner les 2 perimetres)
  demande un arbitrage produit (faut-il elargir la detection ou restreindre le boost ?).
- **Action** : Issue #762 (labels `backend` + `needs-review`), pas de PR (hors perimetre
  "modere" — decision non-triviale).
