## Detail du finding retenu

### cinesort/app/updater.py:118 — `_read_cache` : float(ts) hors try/except

- `_read_cache()` parse `time.time() - float(data.get("ts", 0))` **hors** du `try/except`
  qui ne couvre que `json.JSONDecodeError`/`OSError`.
- Un cache `update_cache.json` tronque (ecriture partielle, crash disque), edite a la main,
  ou contenant `"ts": "garbage"` (-> `ValueError`) ou `"ts": null` (-> `data.get("ts", 0)`
  renvoie `None` car la cle est presente -> `float(None)` -> `TypeError`) fait remonter
  l'exception jusqu'au hook de boot (`check_for_update_async`, thread daemon).
- **Contredit la philosophie explicite du module** : *"cache illisible -> refetch, jamais
  crash"* (cf docstring `_read_cache` ligne 114).
- **Incoherence isolee** : `cinesort/infra/tmdb_client.py:247-250` garde deja son propre
  `float()` de timestamp dans `try/except (TypeError, ValueError)`. L'updater etait le seul
  call-site a ne pas le faire — c'est un drift, pas un choix de design.
- **Severite** : STYLE / robustesse (1) — pas de DoS (thread daemon, l'app survit), mais
  viole l'invariant "jamais crash au boot" + log un traceback non gere.
- **CWE** : CWE-754 Improper Check for Unusual or Exceptional Conditions.
- **Fix** : `try: ts = float(data.get("ts") or 0.0) except (TypeError, ValueError): return None`,
  miroir exact du pattern TMDb. 2 tests de regression (`ts` non-numerique + `ts=null`) qui
  erraient avant le fix.
- **Action** : PR #675.
