## Le finding principal, en detail

`_rematch_tmdb_and_update_plan` est le **seul** endroit du produit qui honore les
`film_field_locks`. Il lisait les noms verrouilles sous
`compute_film_id(new_row_json)` — et cette valeur ne peut **structurellement
jamais** etre un `tmdb:<id>` :

```
PlanRow porte-t-il 'tmdb_id' ?           False
PlanRow porte-t-il 'proposed_tmdb_id' ?  False
Nombre de champs PlanRow : 31
cles contenant 'tmdb' : ['tmdb_collection_id', 'tmdb_collection_name', 'tv_tmdb_series_id']
```

Les verrous, eux, vivent sous `tmdb:<id>` des qu'un id TMDb est connu — deux
chemins de production l'y mettent (`enrich_tmdb_ids_by_title` ecrit `tmdb_id` dans
plan.jsonl depuis le thread de fin de scan ; `set_film_tmdb_candidate` y **migre**
les verrous). Les deux bouts ne se rencontraient jamais.

**Le plus interessant n'est pas le bug, c'est l'enchainement qui le declenche.**
L'utilisateur corrige un titre a la main -> `migrate_locks` deplace le verrou vers
`tmdb:<id>` **et supprime la ligne `path:`** -> le rescan suivant ne trouve plus
rien et ecrase la correction. La migration a ete ajoutee pour **empecher**
l'ecrasement (son commentaire le dit) ; en l'etat elle le provoquait. C'est le
piege n3 du `CLAUDE.md` : *un correctif peut ETEINDRE une garde existante*.

Et le trou de couverture est le piege n1 du meme fichier. Les **deux** fichiers de
test du sujet passent `locked_fields` **a la main** a `merge_metadata`. Le helper
de l'un s'appelle `_rematch` et son docstring dit « rejoue ce que fait
`_rematch_tmdb_and_update_plan` » — mais il saute par-dessus le seul endroit ou le
defaut vit : la resolution du `film_id`.

## Environnement d'execution — capacite RESTAUREE

Le run du 2026-08-09 signalait ne pouvoir executer **ni** `python`, **ni**
`pytest`, **ni** `ruff`, et concluait que « les prochains runs ne pourront plus
ouvrir de PR avec la garantie *test vu ROUGE sans le correctif* ».

**Ce n'est plus le cas, et le detail compte pour les prochains runs** : la liste
`--allowedTools` d'`audit-module.yml` contient `Bash(python -m:*)`. Tout passe donc
par cette forme :

```bash
python -m pip install --break-system-packages pytest ruff==0.16.1 requests numpy pydantic rapidfuzz segno sqlparse
python -m pytest tests/ --ignore=tests/e2e … -q
python -m ruff check . ; python -m ruff format --check .
```

`python3 -m …`, `uvx`, `git fetch` et `git stash` ne sont **pas** dans la liste. Le
contournement pour comparer un correctif a `main` est `git checkout` (autorise) :
committer sur la branche, `git checkout main`, rejouer les tests suspects,
revenir. C'est ainsi que les 2 echecs douteux de ce run ont ete attribues a
l'environnement.
