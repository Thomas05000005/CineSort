## Findings

### A1 — la garde « non mesure » de #923 s'arretait a 4 criteres sur 8 *(sev. 2, corrige)*

`compare_criterion` porte depuis #923 les parametres `measured_a`/`measured_b`,
et sa docstring pose la regle. `build_comparison_report` les passait pour
blockiness, blur, banding et profondeur effective — et pour aucun des quatre
autres.

| Critere | `higher_is_better` | valeur si non mesure | garde | sens de l'erreur |
|---|---|---|---|---|
| Artefacts / Nettete / Banding | False | 0.0 | ✅ | — |
| Profondeur effective | True | 0.0 | ✅ | — |
| Detail (variance) | True | 0.0 | ❌ | restrictif |
| Dynamique audio (LRA) | True | `None` -> 0 | ❌ | restrictif |
| Bruit de fond | False | `None` -> 0 | ❌ | restrictif (dBFS negatif) |
| **Clipping** | **False** | **0.0** | ❌ | **PERMISSIF** |

`analyze_clipping_segments` rend exactement
`{total_segments: 0, clipping_pct: 0.0, verdict: "unknown"}` sur ses **trois**
chemins d'echec. Or 0 % de clipping est la valeur PARFAITE :

```
A mesure     : total_segments=120, clipping_pct=3.5  ->  perd
B non mesure : total_segments=0,   clipping_pct=0.0  ->  GAGNE
```

**Le contrat n'a pas ete invente** : `audio_perceptual._compute_audio_score`
porte deja les trois gardes (`if lra is not None`, `if nf is not None`,
`total_segments > 0` — garde R8-098, dont le commentaire dit « une mesure ratee
mappait vers la valeur la plus flatteuse »). `comparison.py` etait le **second**
lecteur de ces trois metriques, et le seul sans la garde.

**Portee reelle, bornee, et il faut le dire** : `build_comparison_report`
alimente `compare_perceptual`, qu'**aucun ecran n'appelle** (le front appelle
`get_perceptual_compare_frames`, `get_perceptual_compare_audio`,
`get_perceptual_report`). Le chemin batch `queue_perceptual_analyses` l'execute
mais **jette** le rapport (`results.append({**pair, "ok": True})`). Le lot ferme
donc un trou AVANT qu'un ecran ne le lise.

**PR #1220.** Cliquet de taille : `build_comparison_report` 174 -> 153 par
EXTRACTION (`_build_audio_criteria`), gain verrouille dans `PLAFONDS`.

### A3 — le genre TMDb est lu sur le premier candidat, pas sur le chosen *(sev. 3, issue #1221)*

`PlanRow.candidates` est stocke dans l'ordre d'INSERTION
(`plan_support_replan.py:851-854` : NFO, puis TMDb, puis nom), et
`pick_best_candidate` (`core.py:1667-1672`) trie une liste **locale** sur
`(score + bonus_consensus, score, annee)`. `candidates[0]` est donc le premier
candidat NFO des qu'il en existe un — jamais le retenu.

Deux sites lisent quand meme le premier :

- `quality_report_support.py:160-165` (premier **avec** un tmdb_id) -> `tmdb_genres`
  -> tout le scoring genre-aware P4.2, et le rapport est **persiste** ;
- `perceptual_support.py:1904-1908` (`candidates[0]` **nu**) -> si le premier
  candidat est un NFO sans `<tmdbid>`, retourne `None` : le grain intelligence
  perd `tmdb_year` / `tmdb_genres` / `tmdb_budget` / `is_animation` /
  `is_major_studio`, donc l'ere du film, donc le verdict DNR. Echec silencieux.

Le depot a **deja tranche** : `runtime_probe_check._get_chosen_tmdb_id` (F24/F27)
a abandonne ce fallback, et sa docstring nomme la cause — « qui diverge du chosen
de `pick_best_candidate` (bonus consensus / disambiguation) ».

**Pas de PR** : `_get_chosen_tmdb_id` refuse de deviner en cas d'ambiguite, donc
le brancher retirerait le scoring genre-aware de ces rows et **deplacerait des
scores persistes** (bump de `SCORING_RULES_VERSION` + arbitrage). Detail dans
#1221, avec la sonde de frequence a executer avant tout correctif.

### A2 — `flag_warning`, une des 7 actions du builder de regles, n'a aucune sortie *(sev. 2, cat. 17)*

Chaine complete, mesuree au `grep` sur `cinesort/` **et** `web/` :

1. `custom_rules._act_flag` (`:294-301`) ajoute `value` a `result["flags_added"]`,
   et `"! <reason>"` a `result["reasons"]` **seulement si `reason` est renseigne** ;
2. `quality_score._apply_custom_rules_helper:2072` -> `custom_flags_added` ;
3. `_build_quality_metrics_helper:2251` -> `"custom_warning_flags"` ;
4. **lecteurs de `metrics.custom_warning_flags`** : **0**. Seule occurrence hors
   producteur : `tests/test_scoring_class_review_2026_08_03.py:518`.

Or `reason` est un champ **libre et optionnel** cote UI
(`regles-qualite.js:328` : `reason: b.action.reason || ""`). **Une regle
`flag_warning` sans motif est donc totalement muette** : l'utilisateur l'a
configuree, elle se declenche, et rien ne change nulle part. Avec un motif, seule
la phrase apparait ; le nom du flag qu'il a choisi n'est jamais montre, ni
filtrable, ni exportable.

Contraste : les six autres actions (`score_delta`, `score_multiplier`,
`force_score`, `force_tier`, `cap_max`, `cap_min`) modifient toutes le score ou
le tier. `flag_warning` est **la seule dont l'effet propre n'atteint aucune
surface**.

Corollaire (principe de moindre surprise, cat. 45) : le champ de condition
`warning_flags` lit `__context__.warning_flags`, alimente par `encode_warnings`
et **jamais** par les flags que les regles posent. Deux regles ne peuvent donc
pas se chainer, alors que le catalogue expose les deux cotes.

**Pas de PR** : exposer le flag demande de decider OU (drawer film ? colonne
filtrable ? export ?) — arbitrage produit. Consigne ici et dans la synthese.
