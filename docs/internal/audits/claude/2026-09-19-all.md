## A1 — Un serveur injoignable n'est pas un film non retrouve *(sev. 2)*

**Corrige : PR #1259.** Persona RELIABILITY. Categorie 2 (bug domaine).

`restore_watched` (`cinesort/app/jellyfin_sync.py`) classe les films non
restaures par cause. Deux se confondaient :

```python
try:
    current_movies = client.get_all_movies_from_all_libraries(user_id)
except (OSError, ValueError, JellyfinError) as exc:
    _log.warning("Jellyfin sync : echec recuperation films (tentative %d) — %s", attempt, exc)
    continue        # <- pending intact, mark_failed intact
```

Quand le serveur ne repond a **aucune** des cinq tentatives (NAS endormi, cable
debranche, service arrete pendant l'apply), `pending` reste plein et
`mark_failed` vide — **exactement l'etat produit par un serveur qui REPOND mais
n'a pas encore re-indexe**. Les deux partaient dans la meme branche :

```python
result.not_found += 1
"reason": "film non retrouve dans Jellyfin apres re-indexation"
```

**Ou ca atterrit.** Apres 135 s d'attente (backoff 5+10+20+40+60), l'utilisateur
lit « N film(s) non retrouve(s) apres re-indexation ». Il est **bien prevenu** —
c'est ce qui separe ce defaut d'un silence, et ce qui le maintient a sev. 2 —
mais le message l'envoie vers un « Force Refresh All Metadata » quand la seule
action utile est de rallumer une machine.

**La mesure qui debloquait le finding.** Le rapport d'hier refusait d'ouvrir une
PR faute de connaitre les lecteurs de `not_found`. Ils sont trois, et aucun ne
s'en sert comme preuve :

| Lecteur | Nature |
|---|---|
| `jellyfin_sync.py:106` (`to_dict`) | serialisation |
| `jellyfin_sync.py:507` | log interne |
| `apply_support.py:3146` | **seul lecteur applicatif** : `if not_found > 0: log WARN` |
| `web/` | **zero** |

**Le point de conception, et il compte plus que le correctif.** Sortir ces films
de `not_found` **sans message dedie** les aurait fait passer d'un diagnostic faux
a un **SILENCE** — le piege « un correctif peut ETEINDRE une garde existante »,
paye ici en sens inverse. Le WARN correspondant est donc ajoute au site d'appel
et verrouille par `LeSiteDAppelPrevientLUtilisateurTests`, dont un contre-test
**refuse le mot « re-indexation »** dans ce message.

**Le critere est volontairement prudent** : une seule reponse du serveur suffit a
conserver `not_found`. Un serveur qui a parle puis s'est tu n'est pas declare
injoignable — sinon le verdict dependrait de l'instant ou le reseau a lache,
pas de ce qu'on sait.

**Pourquoi ce n'est pas une sev. 3.** L'apply disque a reussi, rien n'est perdu
sur le disque, et l'utilisateur voit un message. Seuls les statuts « vu » sont
concernes, et le diagnostic est mauvais — pas absent.

## A2 — Le contrat i18n ne scanne que `web/` *(sev. 1, defense en profondeur)*

Persona UX. Categorie 8.

`cinesort/domain/i18n_messages.t()` lit **le meme** `locales/<locale>.json` que
le front, et son contrat en cas de cle absente est ecrit dans sa docstring :

> « si une cle est manquante, `t(key)` retourne `key` (pas de crash) »

Une cle manquante s'affiche donc **en brut** a l'utilisateur
(`notifications.title_incoherence_apply` au lieu du message). Or
`tests/test_contract_i18n.py` annonce son perimetre des sa docstring : « toute
cle i18n referencee statiquement dans **web/** ». Le Python n'y est pas.

**Mesure du jour — et elle disculpe l'etat courant :**

| Controle | Resultat |
|---|---|
| Cles `t("...")` litterales sous `cinesort/` + `app.py` | **89** |
| Absentes de `fr.json` | **0** |
| Absentes de `en.json` | **0** (le contrat 2, parite stricte fr/en, les couvre indirectement) |
| Cles a interpolation dont l'appelant oublie un `{{var}}` | **0** (les 18 sites verifies un par un) |

Le trou de perimetre est **reel**, le defaut observable est **nul**. C'est donc
un finding de defense en profondeur, et il est presente comme tel — pas comme
un defaut qu'on aurait trouve.

**Effet de bord a connaitre** : le meme contrat documente « 519 cles orphelines
(definies mais jamais referencees) — decision produit en attente ». Ce compte est
etabli sur les references de `web/` seules : **les 89 cles Python en font
partie**. Le chiffre surestime donc les orphelines reelles, et quiconque s'en
servira un jour pour supprimer des cles doit le savoir.

**Pas de PR** : etendre l'extraction d'un contrat a marge zero est un changement
de garde, pas un correctif. Le faire sans pouvoir executer le test ferait courir
le risque exact que ce depot a deja paye (« un garde plus faible qui dilue le
vrai »). L'etat mesure etant conforme, le cliquet naitrait verrouille — c'est
justement ce qui rend la PR facile a ecrire **pour qui peut la lancer**.

## Modules disculpes — la partie la plus reutilisable

La question « que fait cette garde quand elle ne peut pas garder ? » a ete posee
a chacun. Tous y repondent deja correctement.

| Module | Ce qui le disculpe |
|---|---|
| `infra/security/secret_storage` | Echoue **fermé** partout : `SecretStorageError` sur blob illisible, base64 invalide, ou DPAPI-NG indisponible. Le seul chemin tolerant est le re-chiffrement silencieux apres une lecture legacy REUSSIE — la valeur est deja en main, ne pas la rendre serait une perte gratuite, et c'est ecrit |
| `infra/security/dpapi_ng` | Les buffers NCrypt sont liberes par `LocalFree` dans un `finally`, le descripteur ferme dans un second `finally`, et le magic de format evite un dechiffrement d'essai. `dpapi_ng_available()` ne devine pas : il tente le chargement |
| `infra/fs_safety` | `run_with_timeout` rend le `default` sur timeout **et** sur exception, et `safe_path_exists` expose un vrai tri-etat (`None` = pas de reponse). `read_text_bounded` verifie la taille AVANT lecture **puis** re-verifie sur le flux — le TOCTOU est nomme dans la docstring |
| `infra/subprocess_safety` | Le cleanup est garanti par `finally` y compris si `_register` leve (`BaseException` rattrapee, child tue, exception relancee), et `atexit` couvre le shutdown gracieux. La limite — SIGKILL externe — est ecrite, avec la solution qu'il faudrait (job object Windows) |
| `infra/db/pragma_profile` | `detect_storage_type` retombe sur `local_ssd` (le profil le **moins** penalisant pour une DB locale) a chaque echec, et `nas_smb_slow` n'est jamais choisi par l'autodetect : il exige un override explicite, « l'utilisateur sait mieux que nous » |
| `app/verdicts` | Module pur, sans E/S. Chaque `Incoherence` porte les **grandeurs** qui l'ont produite, et les invariants inatteignables sont ETIQUETES comme tels dans le module lui-meme |
| `ui/api/_run_state` | Les deux verrous sont distincts par conception (mutation memoire vs I/O fichier), et le handler de secours du `log()` ne peut pas se deadlocker : le `with` du bloc principal a relache `_file_log_lock` avant que l'exception n'atteigne le `except` |
| `infra/db/repositories/decisions` | `upgrade_deferred_to_accepted` a une liste blanche **fermee** : `rejected` est refuse nommement (inverser vers un etat apply-able est destructif), et le TOCTOU restant est documente avec ses deux remedes possibles |
| `domain/resolution_class` | `RES_UNKNOWN` quand aucune dimension n'est exploitable, et `is_below` refuse de juger une classe inconnue. `OverflowError` est dans le tuple d'exceptions parce que `json.loads` accepte `Infinity` — le raisonnement est ecrit, et c'est le meme piege que la regle n°4 du CLAUDE.md |
