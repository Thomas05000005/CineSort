## Corrige — PR #1255

### A1 — Un snapshot Jellyfin IMPOSSIBLE etait annonce comme « aucun film vu » *(sev. 3)*

`snapshot_watched` (`cinesort/app/jellyfin_sync.py:255`) attrape **toute**
exception du client et rendait `{}` — la MEME valeur qu'une bibliotheque ou
aucun film n'est marque comme vu. Les deux cas partaient ensuite dans le meme
silence :

```python
# apply_support.py:3103  (avant)
snapshot = snapshot_watched(client, user_id)
if snapshot:                        # {} est falsy -> AUCUN log
    log_fn("INFO", f"Jellyfin sync : {len(snapshot)} film(s) vu(s) sauvegardé(s).")
return {"snapshot": snapshot, ...}  # contexte VALIDE, snapshot vide

# apply_support.py:3124
if not snapshot:
    return                          # sortie silencieuse totale
```

**Ou ca atterrit.** L'apply, lui, deplace bien les fichiers. Jellyfin cle ses
items **par chemin** — c'est ecrit noir sur blanc dans le module d'a cote
(`update_played_state`, #535 : « Jellyfin ré-indexe un item NEUF (les items sont
clés par chemin) »). Il re-indexe donc des items neufs et les statuts « vu »
sont perdus, **definitivement**, sans que rien ne les restaure. Le journal
d'apply ne porte pas une ligne a ce sujet.

**La garde existait, quatre lignes plus bas.**

```python
except (IntegrationError, OSError, requests.RequestException) as exc:
    log_fn("WARN", f"Jellyfin sync : échec snapshot — {exc}")
```

Elle etait **INATTEIGNABLE pour le seul chemin qui echoue vraiment** :
`snapshot_watched` avale l'echec AVANT elle et la prive de sa matiere. C'est
exactement le motif de **#1097** (« la garde du backend etait CORRECTE mais
INATTEIGNABLE ») et de **#1083** (« une garde peut en aveugler une autre en
s'executant avant elle »).

**Ce qui l'a masque** : `_make_jellyfin_client` ne fait aucun appel reseau
(constructeur pur, verifie), et `jellyfin_user_id` est en settings des le
premier test de connexion reussi. Le PREMIER appel reseau du chemin snapshot est
donc precisement celui qui est avale. Serveur eteint = silence integral.

**Pourquoi la refutation du 2026-05-28 ne couvre pas ce finding.** Le rapport de
ce jour-la ecarte `snapshot_watched except Exception` comme « idiomatique,
defensif ». Il a raison **sur la largeur du catch** — ne jamais lever vers
l'apply est le bon contrat. Le present finding ne porte pas sur le catch mais
sur la **valeur rendue** : le meme `{}` pour deux etats du monde. Le correctif
conserve le catch large.

**Le remede ne rend pas l'apply bloquant** — ce serait un arbitrage produit. Il
rend la distinction possible (`None` = on ne sait pas, `{}` = rien a
sauvegarder) et branche l'annonce sur **le seul appelant de production**
(`apply_support.py:3102`, mesure par grep sur `cinesort/`, `web/` et `app.py`).
Cas « le bon endroit n'est pas le point commun mais le seul appelant qui manque
la garde ».

**Preuve** : 7 tests dont **4 contre-tests**. Le contre-test central — *une
bibliotheque sans aucun film vu ne declenche AUCUNE alerte* — est **vert des
deux cotes** : c'est ce qui prouve que l'alerte vise l'IGNORANCE et non
l'absence. Sans lui, le correctif crierait au loup a chaque apply d'une
bibliotheque neuve.

Deux pieges du depot evites et documentes dans l'entete du fichier de test : le
**mock qui fabrique la condition testee** (les clients sont de vraies classes) et
**tester la decision sans son site d'appel** (les tests de journalisation
patchent le CLIENT, pas `snapshot_watched`, pour qu'un mutant supprimant l'appel
meure).

## Corrige — PR #1256

### A2 — Un score de 0 — le PIRE fichier — n'etait jamais propose en upgrade Radarr *(sev. 2)*

```python
# cinesort/app/radarr_sync.py:158 (avant)
score = int(quality_report.get("score") or 0)
if score > 0 and score < _UPGRADE_SCORE_THRESHOLD:   # seuil = 54
    return True
```

Le `> 0` n'ecartait **pas** une valeur manquante : sur le chemin de production,
`repositories/quality.get_quality_report` fait `int(row["score"])` — la cle est
**toujours** presente. Il ecartait la NOTE **0**, bas de l'echelle `[0, 100]`
que `quality_score._clamp_0_100` garantit.

Le seul film que Radarr ne se voyait donc jamais proposer en upgrade **par le
critere du score** etait le plus mauvais de la bibliotheque.

Meme famille que **#1216** (« `.get(cle, 0)` confond *inconnu* et *pire* »),
prise par l'autre bout : ici c'est *le pire* qui etait traite comme *inconnu*.

**Ce n'est pas theorique** : #1067 a mesure un score 0 en production (un
`cap_max` non numerique posait un plafond a 0 — score 80 -> 0, tier Reject,
`motifs: []`). Un tel film reste rattrapable par les criteres codec obsolete /
flags d'encode, **sauf** s'il porte un codec moderne sans defaut d'encode.

**Ce que le correctif ne change pas** : cle absente, seuil 54 exclusif, entrees
int / float / chaine numerique. Durcissement annexe : `int("abc" or 0)` levait
une `ValueError` qui remontait jusqu'a `get_radarr_status` et emportait tout le
rapport ; on rend desormais « on ne sait pas ».

**Preuve** : 10 tests dont 4 contre-tests verts des deux cotes. Le fichier de
reference porte un encodage SAIN, **verifie par un test** (`analyze_encode_quality(...) == []`)
et non suppose, pour que les deux autres criteres soient muets — « asserter ce
que SEUL le correctif produit ». Deux tests jouent `get_upgrade_candidates`, le
site d'appel reel.

## Signale sans PR — la raison compte autant que le constat

### A3 — Un serveur injoignable est compte en « film non retrouve apres re-indexation » *(sev. 2)*

Pendant exact de A1, cote restauration. Dans `restore_watched`
(`jellyfin_sync.py:354`), l'echec de rapatriement consomme une tentative :

```python
except (OSError, ValueError, JellyfinError) as exc:
    _log.warning("Jellyfin sync : echec recuperation films (tentative %d) — %s", attempt, exc)
    continue
```

Si les **5** tentatives echouent (serveur toujours eteint, 135 s plus tard), les
films restes en attente tombent dans la boucle finale et sont comptes
`not_found`, avec la raison `"film non retrouve dans Jellyfin apres
re-indexation"`.

L'utilisateur EST prevenu — c'est ce qui separe A3 de A1, et ce qui le fait
descendre a sev. 2 — mais le message **oriente le diagnostic vers Jellyfin et
son indexation**, alors que la cause est le reseau. Il cherchera du cote d'un
« Force Refresh All Metadata » au lieu de rallumer son NAS.

**Pas de PR** : le remede propre est un troisieme compteur dans `RestoreResult`
(`unreachable`), donc un champ de plus dans `to_dict()` — un payload lu ailleurs.
Or ce depot a deja paye « rendre un compteur honnete l'a mis a zero chez son
lecteur, qui s'en servait comme preuve ». Il faut d'abord greper les lecteurs de
`not_found` ; c'est plus qu'un correctif sur.

### A4 — `plex_client.get_movies_count` rend `0` sur erreur — mais n'a aucun appelant de production *(sev. 1)*

```python
except (PlexError, ValueError, KeyError):
    return 0
```

Le motif est bien celui du jour (un echec rendu comme un comptage), et il
contraste avec son jumeau `jellyfin_client.get_movies_count` qui, lui, **leve**.

**Mais le chemin est inatteignable** : les deux seuls appels de
`get_movies_count` dans `cinesort/` (`cinesort_api.py:1507`,
`settings_support.py:2414`) portent sur un **JellyfinClient** — ils passent un
`user_id`, la signature Plex prend un `library_id`. Mesure faite avant d'ecrire,
pas apres.

C'est donc une asymetrie dormante, a corriger le jour ou la methode sera cablee,
pas un defaut observable. Notee ici pour qu'elle ne soit pas re-instruite comme
un bug actif.

### A5 — `_normalize_endpoint` d'Ollama resout le DNS la ou ses trois freres s'en abstiennent *(sev. 1)*

`jellyfin_client`, `plex_client` et `radarr_client` appellent tous
`is_safe_external_url(url, resolve_dns=False)` avec le meme commentaire de dix
lignes : resoudre le DNS au moment ou l'utilisateur ENREGISTRE son URL rend
l'appel bloquant (`socket.getaddrinfo` ne respecte pas
`socket.setdefaulttimeout`).

`ollama_client._normalize_endpoint:114` appelle `is_safe_external_url(endpoint)`
**sans** ce parametre — donc avec le defaut `resolve_dns=True`.

Consequences bornees, et c'est pourquoi il n'y a pas de PR : le flag
`AI_ENRICHMENT_FEATURE_FLAG` est **OFF**, l'endpoint par defaut est
`localhost:11434` (resolution instantanee), et la garde de connexion
`SsrfGuardHTTPAdapter` reste en vigueur dans tous les cas. Le jour ou la feature
s'active avec un endpoint LAN, l'asymetrie coutera un blocage a l'enregistrement
des reglages.

### Confiance < 0,70 — pas d'issue

- **Timeout scalaire + `stream=True`** : `timeout=self.timeout_s` borne une
  lecture de socket, pas la duree totale du corps. Un pair qui envoie un chunk
  toutes les 9 s tient donc la connexion bien au-dela. `poster_proxy` a deja
  traite exactement ce cas (`STREAM_BUDGET_S = 20.0`, avec la mesure : *641
  lectures, 5769 s de thread retenu pour UNE jaquette*), mais les clients
  JSON ne l'ont pas. Non signale : leurs corps sont bornes a 10 Mo et aucun ne
  tourne dans un thread du serveur REST — le profil de risque de `poster_proxy`
  n'est pas le leur. A re-mesurer si un de ces clients passe en thread REST.
