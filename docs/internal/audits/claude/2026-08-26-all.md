## A1 — BUG : une santé de 0 s'affichait 100, donc l'alerte ne partait jamais

**Persona** : UX + RELIABILITY. **Catégorie** 2 (sentinel value confusion) + 19 (cohérence backend↔UI).
**Confiance** 0,95. **Corrigé — PR #1146.**

`cinesort/ui/api/dashboard_support.py:1866` :

```python
health = int(librarian_data.get("health_score") or 100)
if health < 60:
    insights.append({... "type": "health_low" ...})
```

Python évalue le **falsy**, pas l'absence. `0 or 100` vaut `100`.

Le comportement était **non monotone** — et c'est ça qui le rend visible :

| `health_score` rendu par le domaine | valeur lue par l'écran | alerte |
|---|---|---|
| 59 | 59 | oui (`info`) |
| 39 | 39 | oui (`warning`) |
| **0** | **100** | **aucune** |

### Pourquoi 0 est atteignable

`cinesort/domain/librarian.py:404` rend `round(100 * healthy / total_rows)`. Le bloc C
(« sous-titres manquants », `librarian.py:250`) marque comme *à problème* toute ligne à laquelle il
manque une langue attendue — `fr` par défaut (`librarian.py:150`). Une bibliothèque anglophone, ou
simplement celle d'un utilisateur qui ne télécharge pas de sous-titres, met **toutes** ses lignes
dans `problem_ids` : `healthy = 0`.

Ce n'est pas une déduction. `tests/test_lot_librarian_rules_617_662_723.py:147` asserte déjà :

```python
self.assertEqual(generate_suggestions(rows, reports, {})["health_score"], 0)
```

Le domaine produisait bien 0 ; c'est la couche `ui` qui le relevait à 100.

### Où ça atterrit

`get_global_stats` (`:2053`) passe le résultat à `_compute_active_insights`, dont la sortie part en
`:2076` dans `notifications_support.emit_from_insights` — le **centre de notifications**, seul canal
qui survit à la fermeture de l'écran (`CLAUDE.md`, « Où l'incohérence atterrit »). `emit_from_insights`
ne filtre pas sur `count` : l'insight supprimé ici n'était émis **nulle part**.

### Vérification adversaire

- *déjà corrigé ?* Non — ligne lue sur `main` avant d'écrire.
- *la garde existe ailleurs ?* Non. Les trois autres lecteurs de `health_score`
  (`:1472`, `:1475`, `:1483`, `:2026`) filtrent sur `is not None` et sont **inchangés**.
- *chemin inatteignable ?* Non, cf. ci-dessus.
- *qui d'autre lit cette valeur ?* Seul le calcul de sévérité `"warning" if health < 40 else "info"`,
  qui redevient juste du même coup.

### Contrainte rencontrée

`_compute_active_insights` est sous **plafond de taille** (`tests/test_function_size_budget.py:145`,
176 lignes, marge zéro). Le correctif remplace donc **deux lignes par deux lignes** ; la
justification longue vit dans la docstring du test.

## A2 — BUG : le repli `cp1252` des NFO était inatteignable

**Persona** : RELIABILITY. **Catégorie** 11 (code mort) + 2 (bug domaine) + 37 (Unicode).
**Confiance** 0,90. **Corrigé — PR #1147.**

`cinesort/domain/core.py:955` (`parse_movie_nfo`) :

```python
for enc in ("utf-8", "latin-1", "cp1252"):
```

Le codec `latin-1` mappe les **256** valeurs d'octet : il ne lève **jamais** `UnicodeDecodeError`.
Placé en deuxième, il rendait le troisième élément **inatteignable**. `cp1252` était du code mort,
et le repli réel était latin-1 pour *tous* les NFO non-UTF-8.

### Pourquoi ce n'est pas cosmétique

Les deux jeux ne diffèrent que sur `0x80-0x9F` — exactement là où Windows range la ponctuation
typographique :

| octet | cp1252 (voulu) | latin-1 (obtenu) |
|---|---|---|
| `0x92` | `U+2019` ’ | `U+0092` (contrôle C1) |
| `0x93` / `0x94` | `U+201C` / `U+201D` | `U+0093` / `U+0094` |
| `0x96` | `U+2013` – | `U+0096` |
| `0x80` | `U+20AC` € | `U+0080` |

### Le chemin jusqu'au disque

1. `core.build_candidates_from_nfo:1162` fait du titre un `Candidate(source="nfo", score=0.90)` —
   un candidat de **haute confiance**.
2. S'il l'emporte, il devient le `proposed_title`, donc le **nom de dossier**.
3. `path_utils.windows_safe:106` ne retire que `[\x00-\x1f\x7f]` : **la plage C1 n'est pas filtrée**,
   et NTFS l'accepte dans un nom.

Le caractère de contrôle survit donc jusque sur le disque, dans un dossier qui *paraît* correct dans
l'Explorateur. C'est la **règle 2** du `CLAUDE.md`. Effet de bord : un titre mojibake fausse la
comparaison TMDb et peut lever un `nfo_title_mismatch` (`core.py:1539`) sans raison.

### Vérification adversaire

- *déjà corrigé ?* Non — tuple lu sur `main`.
- *la garde existe ailleurs ?* Non. `grep -rn "latin-1|cp1252" cinesort/` : **1 seule** occurrence de
  production. Les deux fichiers de test qui référencent `parse_movie_nfo`
  (`test_error_resilience.py`, `test_domain_core.py`) ne couvrent aucun encodage.
- *chemin inatteignable ?* Non : il suffit d'un NFO non-UTF-8 portant un octet `0x80-0x9F`.

### Ce que le correctif ne fait PAS

Il ne touche qu'à l'**ordre**. `latin-1` reste dernier et reste **atteignable** — cp1252 laisse cinq
octets indéfinis (`0x81`, `0x8D`, `0x8F`, `0x90`, `0x9D`) sur lesquels il lève. Un contre-test
l'interdit explicitement de disparaître.

## B1 — QUALITY : `OverflowError` hors du tuple, sur trois coerceurs « tolérants »

**Persona** : RELIABILITY. **Catégorie** 1 (bug latent) + 14 (error handling). **Confiance** 0,85.
**Décrit ici, pas de PR.**

Ce dépôt a **déjà appris** que `int(float("inf"))` lève `OverflowError` — qui dérive
d'`ArithmeticError`, **pas** de `ValueError`. La leçon est écrite deux fois, longuement, et rattachée
explicitement à la règle 4 du `CLAUDE.md` :

- `cinesort/domain/conversions.py:39-55` (`to_int`) — « le cas est ATTEIGNABLE parce que `json.loads`
  accepte `Infinity` et `NaN` par défaut » ;
- `cinesort/domain/resolution_class.py:50-67` (`_positive_int`) — « `OverflowError` est INDISPENSABLE
  dans le tuple » ;
- et une troisième fois dans `conversions.to_optional_int:126-131`, sur `round()`.

Elle n'a été portée à **aucun** des trois coerceurs restants :

| Site | Expression | Tuple `except` | Conséquence |
|---|---|---|---|
| `domain/conversions.py:163` `to_optional_bitrate` | `int(round(value))` | *aucun* | lève sur `inf` **et** sur `nan`, là où son frère `to_optional_int` rend `None` |
| `ui/api/settings_support.py:87` + `:91` `_coerce_int_with_default` | `int(float(cleaned))`, `int(value)` | `(TypeError, ValueError)` | contredit son propre contrat « ValueError/TypeError → default » |
| `ui/api/_validators.py:117` `clamp_non_negative_int` | `int(float(value))` | `(TypeError, ValueError)` | asymétrique avec `clamp_timeout` **du même fichier**, qui filtre `inf` explicitement (`:96`) |

L'asymétrie de `_validators.py` est la plus parlante : l'auteur a pensé à `inf` pour `clamp_timeout`
et l'a oublié dix lignes plus bas.

**Atteignabilité, honnêtement** : `json.loads` accepte `Infinity` par défaut, donc un corps REST
`{"email_smtp_port": Infinity}` suffit. L'impact réel est faible — la frontière `except Exception`
de `rest_server.py:1442` transforme ça en HTTP 500 au lieu d'un repli propre. C'est un défaut de
**contrat**, pas une perte de données ; d'où l'absence de PR et la sévérité 2.

**Correctif proposé** (3 lignes, sans arbitrage) : ajouter `OverflowError` aux deux tuples et envelopper
`int(round(value))` de `to_optional_bitrate` comme le fait déjà `to_optional_int` juste au-dessus.

### Écarté dans la même famille

`domain/perceptual/video_analysis.py:129` (`_to_int`) fait aussi `int(float(raw))` sans garde, **mais
ses quatre appelants ne lui passent que des captures de `([\d.]+)`** (`_RE_YAVG`, `_RE_YMIN`,
`_RE_YMAX`, `_RE_SATAVG`, lignes 57-60) : `"inf"` ne peut pas franchir le regex. Non-finding.

## D2 — QUALITY : le circuit breaker du probe ne voit pas les lecteurs réseau mappés

**Persona** : RELIABILITY. **Catégorie** 41 (résilience réseau) + 14. **Confiance** 0,85.
**Consigné en commentaire de #1149 — budget d'ouverture consommé.**

`infra/probe/_source_circuit_breaker.py` existe pour une raison chiffrée dans sa propre docstring :
sans lui, *« un NAS / partage UNC injoignable fait payer 30 s de timeout PAR FICHIER. Sur 5000 films
d'une biblio réseau qui tombe en panne, c'est ~41 h de hang inutile »*.

Or `extract_network_source:58` ne reconnaît que l'**UNC littéral** :

```python
normalized = path_str.replace("/", "\\")
if not normalized.startswith("\\\\"):
    return None          # -> aucun breaker
```

Une bibliothèque sur `Z:\Films` — un partage SMB **monté en lecteur réseau**, la façon la plus
courante de monter un NAS sous Windows — retourne donc `None`, et les cinq points d'appel du breaker
(`:175`, `:201`, `:229`, `:245`, plus `service.py:487`) deviennent des no-op. Le scénario des 41 h
que ce module existe pour empêcher reste entier.

### Le dépôt sait pourtant faire cette détection

`infra/db/pragma_profile.detect_storage_type:185` interroge `GetDriveTypeW` et teste
`DRIVE_REMOTE (4)`. Son commentaire dit mot pour mot : *« UNC pur ne devrait pas tomber ici
(intercepté plus haut), mais on couvre `Z:` -> `\\nas01` »*. La capacité est donc **déjà écrite, dans
`infra/`**, à un import légal de `infra/probe/` (contract `infra_bounded` respecté).

C'est le même angle mort que celui corrigé en **#991** pour `db_local_guard`, décrit alors comme
« aveugle aux lecteurs réseau mappés ».

### Vérification adversaire

- *déjà corrigé ?* Non — fonction lue sur `main`, `return None` inconditionnel hors UNC.
- *la garde existe ailleurs ?* Non pour ce chemin. `adaptive_timeout` borne **une** sonde à 300 s ;
  il n'empêche pas de la répéter fichier après fichier — il aggrave même le cas.
- *chemin inatteignable ?* Non.
- *ce que le test existant en dit* : `tests/test_probe_circuit_breaker.py:47-48` asserte que `C:\` et
  `D:\` rendent `None`. L'intention écrite est « les chemins locaux ne sont pas surveillés » ; `Z:`
  tombe dans la même règle **sans être local**, et aucun cas de test ne le distingue.

### Pourquoi pas de PR, au-delà du budget

Le correctif demande un **arbitrage** : la clé de regroupement d'un lecteur mappé doit-elle être la
lettre (`z:`, simple, suffisant pour agréger les échecs) ou la cible UNC résolue (`\\nas\films`, plus
juste si deux lettres pointent le même partage, mais exige `WNetGetConnection`) ? Les deux se
défendent, et le prompt d'audit réserve les PR aux correctifs « sans arbitrage produit ».
